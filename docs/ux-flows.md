# 北京挂号雷达 UX 流程与 OpenDesign 原型 brief

> 文档状态：当前实现流程 + 历史未来原型参考
>
> 依据：`docs/source-requirements.md`、migration 18 catalog 与 source manifest
> 产品边界：浏览 11 家医院目录；协和东单皮肤科为 stable public-source，安贞朝阳冠心病中心和心律失常中心为 experimental public-source，同仁崇文门鼻科为 rules-only，其余 41 个 target 为 directory-only。产品不承诺实时余号、退号或自动预约，不代替用户登录、验证、实名、医保确认或付款。
>
> **阅读约定：第 4.2 节是当前任务创建事实；第 5 节以后的复杂向导、实时状态与 OpenDesign 画板是未来原型参考，不表示当前 target 已启用。实现与文案冲突时，以 catalog `supportMode/canCreateWatchTask`、精确 manifest binding 和当前 UI 为准。**

## 0. 已确认的产品与运行前提

### 0.1 产品决策

1. 首版为稳定开源版，界面显示版本、许可证、源码与问题反馈入口。
2. 产品仅在用户本机运行。Web 管理端默认只允许本机访问，不提供云端账号、云同步、团队、成员或多用户 SaaS 能力。
3. 明确不使用 Docker。首次配置和系统状态分别检查本机安装的依赖与进程，不出现容器、镜像、Docker Compose 或云部署入口。
4. 首版按单一所有者使用设计，不引入席位或复杂 RBAC。
5. 形态按桌面优先、窄屏可操作的响应式 Web 管理端设计。响应式不等于开放远程访问，默认不得为了手机访问而暴露本机端口。
6. 默认时区固定为 `Asia/Shanghai`，界面统一显示“北京时间”。
7. 日期关注范围默认未来 7 天，最长 14 天。
8. 数据来源首先按 target 的 `public-source/rules-only/directory-only` 展示，并在精确来源存在时补充 `stable/experimental` 与 `sourceId`。A/B/C access class 只作为技术边界，不再替代 target support。

“仅本地运行”指应用、配置、历史记录和脱敏快照保存在本机。访问医院官方来源和外部通知渠道仍需要网络连接。

### 0.2 尚未确定项的 UX 兼容方式

| 待决策 | UX 兼容策略 |
|---|---|
| 首个真实通知渠道 | 统一使用“通知渠道”组件，只展示实际已接入的渠道；未接入渠道不伪装成可选项 |
| 首批来源采用 A 级公开源或 B 级本机浏览器 Agent | 每个来源明确标注“公开信息”或“依赖本机浏览器”，并提供对应自检与恢复动作 |

### 0.3 稳定开源版安全基线

- 默认监听本机回环地址。检测到非本机访问时阻止进入管理端，并显示“此开源版仅允许本机访问”。
- 首次配置明确提示不要将管理端端口暴露到公网或局域网，不提供反向代理、远程访问或公网部署引导。
- 通知渠道密钥只在本机保存，界面默认掩码显示。复制诊断信息时自动排除密钥、Cookie、Token、医院账号与个人身份信息。
- 提醒用户不要把包含密钥的配置文件提交到 Git 或公开问题单。
- 开源版不构成医院服务承诺。医院规则和页面可能变化，所有号源结论均需在官方渠道再次确认。
- 更新或安装第三方适配器前显示来源、版本和权限范围，不以“官方插件”描述未经医院认可的社区适配器。

## 1. 体验目标与设计原则

### 1.1 用户要快速回答的四个问题

进入产品后，用户应在 15 秒内回答：

1. 这家医院、院区、科室是公开来源、规则提醒，还是仅目录？
2. 这个精确 target 能否创建任务，最近一次来源成功是什么时候？
3. 未来 14 天有哪些真实记录且精确匹配 target 的规则？
4. 我该去哪个 HTTPS 官方渠道自行核验和预约？

### 1.2 设计原则

1. **可信度先于热闹感**：每条规则和检测结果都带来源、检测时间或核验时间。未知状态不能显示为“无号”。
2. **时间语义必须明确**：始终区分“放号发生时间”“可预约就诊日期”“检测时间”“最后成功时间”。
3. **官方出口始终可见**：有号提醒和任务详情都提供官方入口，并清楚说明后续操作由用户本人完成。
4. **异常可恢复**：失败状态说明影响、保留最后已知结果、给出下一步，不只展示错误码。
5. **克制查询**：不提供鼓励连续点击的“立即刷新”。允许恢复性重试时，显示冷却与下一次可检测时间。
6. **隐私边界显性化**：不要求输入身份证、医保卡、医院账号密码、Cookie 或 Token。
7. **状态不只靠颜色**：状态点、图标、文字标签和时间共同表达结果。
8. **内容优先于卡片**：采用高信息密度的列表、时间线和分区，不把每段信息都包成相同卡片。
9. **本地边界默认安全**：不以便利为由引导用户开放端口。所有配置、自检、诊断与恢复都以本机运行环境为前提。

## 2. 用户与核心任务

### 2.1 主要用户

北京就医需求明确的个人用户，已经知道目标医院、院区或科室，需要同时掌握放号规则和号源变化。用户可能不熟悉技术术语，但对医院、医生、日期和上午/下午非常敏感。

### 2.2 核心任务优先级

| 优先级 | 用户任务 | 成功标准 |
|---|---|---|
| P0 | 浏览目录并识别支持边界 | 11 家医院按医院 → 院区 → 科室级联；directory-only 清楚说明不可创建 |
| P0 | 创建关注任务 | 只有 `canCreateWatchTask=true` 的精确 target 可提交；公开来源只订阅新排班，规则来源只建规则提醒 |
| P0 | 收到提醒并前往官方渠道 | 提醒包含检测/核验时间、排班或规则摘要、官方入口和风险说明 |
| P0 | 判断来源是否正常 | 可见精确 target/sourceId、stable/experimental、最近成功和失败原因 |
| P1 | 查看放号规则 | 能按未来 14 天理解何时放号，以及对应可预约哪天 |
| P1 | 暂停、编辑或删除任务 | 操作结果明确，可从误删中恢复 |
| P1 | 修复本机 Agent 或通知渠道 | 用户能在原页面完成诊断与恢复 |

## 3. 信息架构

### 3.1 桌面应用壳

桌面端采用左侧导航加主工作区，不设置营销式首页。

**左侧主导航**

1. 总览
2. 关注任务
3. 规则日历
4. 监控状态
5. 通知
6. 设置

**左侧底部常驻信息**

- 固定标识“本机运行”
- 系统健康状态，例如“运行正常”或“1 项需要处理”
- 数据更新时间
- “开源版与安全”入口

**主工作区页头**

- 页面标题与一句任务导向说明
- 当前页关键操作，例如“创建关注任务”
- 全局状态不放入每页重复展示，仅在异常时出现可关闭但可再次找到的状态横幅

### 3.2 站点地图与建议路由

```text
首次本地配置 /setup
  开源版安全确认 /setup/safety
  本机运行自检 /setup/local
  数据源自检 /setup/sources
  通知渠道自检 /setup/notifications
总览 /overview
关注任务 /tasks
  创建任务 /tasks/new
  任务详情 /tasks/:taskId
  编辑任务 /tasks/:taskId/edit

  规则详情侧栏，不强制新路由

  来源详情 /monitoring/sources/:sourceId

  通知渠道 /settings/notifications
  数据与隐私 /settings/privacy
  系统信息 /settings/system

找不到页面 /404

```

### 3.3 状态模型必须分层

界面不得用一个“正常/异常”概括所有状态。

| 维度 | 状态 | 用户含义 |
|---|---|---|
| 任务 | 监控中、已暂停、需要处理、已结束 | 任务本身是否继续执行 |
| 可用性 | 有号、无号、未知 | 最近一次成功检测得到的号源结论 |
| 检测新鲜度 | 刚刚更新、可能延迟、已过期 | 结论是否仍有参考价值 |
| 来源健康 | 正常、恢复中、需要操作、不可检测 | 数据来源能否继续工作 |
| 规则可信度 | 高、中、低、待重新确认 | 放号规则的证据强弱和时效性 |
| 通知 | 已送达、发送中、发送失败、已抑制 | 通知是否真正发出，以及是否被去重或冷却 |

关键规则：

- 检测失败后，可用性必须变为“未知”或保留“上次结果”并标明时间，不能显示成“无号”。
- “最近检测”可能失败，“最近成功”只能指成功获取并解析数据的时间，两者必须分别展示。
- B 级来源中，本机 Agent 离线属于“来源需要操作”，不等于任务被暂停。

## 4. 核心用户旅程

### 4.1 首次本地配置到首个任务

**入口**：用户按开源项目的本机安装说明启动管理端，首次打开 `localhost`。

首次配置采用 5 步引导。每一步都可返回，不把安装日志直接暴露为主要界面。

#### 第 1 步：开源版安全确认

1. 说明产品仅在本机运行，不使用 Docker，也不支持公网部署。
2. 说明开源代码与社区适配器不代表医院官方认可，号源结论需在官方渠道再次确认。
3. 提醒不要提交本地密钥、配置文件或诊断原文到公开 Git 仓库和问题单。
4. 用户勾选确认后继续。

真实文案：

- 标题：“开始本地配置”
- 说明：“北京挂号雷达是本地运行的开源工具。本版本不使用 Docker，所有任务、配置和检测记录保存在这台电脑上。”
- 安全提示：“请勿将管理端端口暴露到公网或局域网。开源版不会代你完成预约，检测结果请以医院官方渠道为准。”
- 确认项：“我了解本工具仅供本机个人使用，不会把配置密钥提交到公开仓库或问题单。”
- 主按钮：“继续检查本机环境”

#### 第 2 步：本机运行自检

系统逐项检查，不要求用户理解容器概念：

- 本地 Web/API 服务
- SQLite 数据库与完整性状态
- 持久任务 Worker
- 本地数据目录读写权限
- 真实通知渠道是否至少启用一个
- Browser Agent 是否完成可选配对

公开来源需要 Playwright fallback 时，安装说明单独引导 `npm run setup:browser`；它不是 PostgreSQL、Redis 或独立 Worker 服务。

每项状态使用“检查中、正常、需要处理、未安装”。失败项显示一条针对本机安装的首选修复动作和可复制诊断编号，不出现 Docker 命令。

真实文案：

- 标题：“检查本机运行环境”
- 正常：“本机服务已就绪”
- 部分失败：“还有 2 项需要处理，已通过的检查不会重复执行。”
- 数据目录失败：“无法写入本地数据目录。请检查目录权限后重新检查。”
- 主按钮：“重新检查失败项”
- 全部通过按钮：“继续检查数据源”

#### 第 3 步：数据源自检

按来源逐行展示医院或平台名称、A/B/C 级能力、当前状态、依赖条件、最后检查时间和受影响功能。自检只执行一次合规检查，不以并发或连续请求测试性能。

- A 级正常：“公开排班可访问，可识别新排班发布；不代表实时有号。”
- B 级待连接：“需要连接本机浏览器。检测结果只写入本机，不上传医院会话信息。”
- C 级受限：“当前仅支持放号规则和定时提醒。”
- 结构变化：“页面内容发生变化，暂时无法确认号源状态。”

至少一个目标来源可用或明确受限后即可继续。失败来源不会阻塞查看规则，但创建任务时必须再次提示能力差异。

#### 第 4 步：通知渠道自检

1. 选择当前版本真实支持的通知渠道。
2. 完成渠道配置，密钥默认掩码且只保存在本机。
3. 系统检查配置完整性和外网连通性。
4. 发送一条测试通知。
5. 用户选择“我已收到测试通知”完成确认。

若渠道服务已接受消息但用户未收到，状态显示“服务已接受，尚未确认送达”，不能写成“通知正常”。用户可跳过并保存草稿，但启用监控前必须至少有一个通过自检的真实渠道。

#### 第 5 步：准备完成

展示本机服务、数据源和通知渠道三组摘要。全部必需项通过后，主按钮为“创建第一个关注任务”。存在非阻塞警告时写清受影响范围。

**成功终点**：任务显示“监控中”，或显示“需要连接本机浏览器”并提供直接恢复动作。

**完成页真实文案**：

- 标题：“本机配置已完成”
- 正文：“现在可以创建关注任务。发现放号或退号变化后，我们会通过已验证渠道提醒你前往官方页面。”
- 边界说明：“不会自动提交预约，也不会要求你上传医院账号、Cookie、身份证或医保信息。”
- 主按钮：“创建第一个关注任务”
- 次按钮：“先查看放号规则”

### 4.2 创建关注任务

**入口**：现在页或任务列表中的“创建关注任务”。

1. 按固定顺序选择医院 → 院区 → 科室；切换上级时自动落到下级目录的第一项。
2. 立即读取该科室的 `targetId/support`，并按精确 manifest binding 补充 `sourceId/stability`，不得按 `hospitalId` 或 access class 推断。
3. `public-source`：显示公开排班边界，允许医生/职称、日期和时段条件；新任务只提交 `schedule_released`。
4. `rules-only`：隐藏医生、职称与时段，规范化为规则提醒 payload。
5. `directory-only`、inactive 或 `canCreateWatchTask=false`：继续允许浏览目录和打开 HTTPS 医院官网，隐藏任务条件、禁用提交并解释“待可靠公开来源”。
6. 日期仍严格限制为北京时间 today..+14d 且连续最多 14 个自然日；成功后进入任务详情。

**兼容分支**：

- 编辑既有实验事件任务时，不展示新的实时能力承诺，但原 `eventTypes` 原样保留；用户切换 target 后重置为该 target 的安全默认。
- 历史任务的 `campusId=null` 通过科室反查真实院区后仍可查看和编辑。
- 支持级别在提交前变化时，服务端返回 `SOURCE_POLICY_VIOLATION`，UI 保留内容并要求重新读取目录。
- 目录 target 不显示“已启用/可监控”，通知渠道是否配置也不能把目录能力升级为来源。

### 4.2.1 当前来源页与规则页

- 来源页遍历 45 个 target，以 `targetId + scope + sourceId` 精确匹配 Adapter；同一 access class 的第一个 Adapter 不能被误绑定。
- 协和显示 stable，安贞两个 binding 显示 experimental，同仁显示 rules-only，其余显示“待可靠公开来源”和医院官网入口。
- 规则页只展示 API 中能与 catalog 医院、院区、科室精确匹配的真实规则，不把规则套给同院其他 target。
- 所有交互使用原生链接、按钮、label/select，键盘可达；桌面与 375px 都保持完整中文医院名称和固定级联顺序。

### 4.3 从提醒到官方预约

**入口**：站内通知或真实外部通知渠道。

1. 用户看到“检测到可用号源”或“发现退号”。
2. 通知展示医院、院区、科室、医生或职称、就诊日期、时段和检测时间。
3. 用户点击“前往官方渠道查看”。
4. 第一次访问该来源时出现轻量确认页，说明即将离开本产品，后续需本人完成登录、验证码、实名和付款。
5. 在新标签页打开官方入口，原页面保留该通知和检测记录。
6. 返回后，用户可标记“已处理”以降低通知中心噪音，但该操作不代表预约成功。

**成功终点**：用户到达已标注来源名称的官方页面。

**禁止文案**：不得使用“已抢到”“锁定号源”“预约成功”等无法证实的表述。

### 4.4 查看规则并创建任务

1. 用户打开规则日历，默认看到未来 14 天的放号事件。
2. 用户按医院、院区和科室筛选。
3. 点击事件查看规则详情、信息来源、最后核验时间和可信度。
4. 点击“按此规则创建任务”。
5. 向导自动带入医院、院区、科室和建议日期，其余字段由用户确认。

### 4.5 监控失败后的恢复

1. 总览和任务详情显示“检测结果可能延迟”，保留最后成功结果及时间。
2. 用户进入监控详情查看失败原因。
3. 系统给出唯一首选动作，例如“重新连接本机浏览器”或“等待自动恢复”。
4. 完成动作后，页面自动重新检查，不要求用户反复刷新。
5. 恢复成功后显示“已恢复检测”，并记录恢复时间。

### 4.6 暂停、编辑和删除

- **暂停**：立即停止后续检测和通知，保留历史。按钮文案为“暂停监控”。
- **恢复**：恢复前检查来源和通知渠道，按钮文案为“恢复监控”。
- **编辑**：保存前展示条件变化摘要。若扩大日期或医生范围，明确提示通知可能增多。
- **删除**：确认文案中写明将删除任务配置但不会影响医院账户。删除后提供 30 秒“撤销删除”。

## 5. 未来原型参考：页面与状态清单

> 本节及后续 OpenDesign 内容保留为未来探索，不是当前支持声明。其中“有号、无号、退号、实时监控、五步向导”等文案只有在具体 target 完成独立来源、隐私与升稳门禁后才能启用；当前 UI 不提供这些新任务事件开关。

### 5.1 页面级清单

| 页面 | 主要内容 | 主操作 | 必须覆盖的状态 |
|---|---|---|---|
| 首次本地配置 | 开源安全确认、本机服务自检、数据源自检、通知渠道自检 | 完成本地配置 | 检查中、可开始、部分失败、通知未确认、Agent 未连接、本地服务不可用 |
| 总览 | 需要处理、近期放号、任务状态、最近通知 | 创建关注任务 | 无任务、正常、部分延迟、全局离线、加载中 |
| 关注任务列表 | 搜索、筛选、任务行、批量仅支持暂停或恢复 | 创建关注任务 | 空、无筛选结果、加载、刷新、部分失败、权限不足 |
| 创建任务向导 | 5 步表单、摘要、来源能力 | 创建并开始监控 | 草稿、字段错误、来源受限、渠道未配置、提交中、提交失败 |
| 任务详情 | 当前结论、检测时间线、条件、通知记录 | 前往官方渠道查看 | 首次检测中、有号、无号、未知、暂停、失败、来源过期 |
| 编辑任务 | 当前条件与变更摘要 | 保存更改 | 未修改、校验失败、并发更新、保存失败 |
| 规则日历 | 未来 14 天规则、筛选、规则详情 | 按此规则创建任务 | 空、加载、过期规则、部分来源失败、无筛选结果 |
| 监控状态 | 本机服务、数据源健康、最近成功、失败数量、Agent 状态 | 运行自检或处理异常 | 全部正常、部分异常、恢复中、外网断开、本地服务不可用 |
| 来源详情 | 来源级别、能力、健康时间线、错误详情 | 执行推荐恢复动作 | 正常、限流、结构变化、Agent 离线、不可检测 |
| 通知中心 | 未读、全部、失败、已抑制通知 | 查看官方入口 | 空、未读、发送中、失败、冷却抑制、加载 |
| 通知设置 | 渠道连接、自检、测试通知、安静时段说明 | 保存并自检 | 未配置、检查中、服务已接受、已确认送达、测试失败、权限被拒 |
| 数据与隐私 | 本地保存范围、脱敏说明、清理操作 | 清理历史快照 | 加载、清理确认、清理中、失败、完成 |
| 系统信息 | 开源版本、本机服务、Worker、数据库、时区 | 运行本机自检 | 正常、部分异常、目录无权限、本地服务不可用 |
| 开源版与安全 | 许可证、源码、问题反馈、安全提醒、诊断脱敏 | 复制脱敏诊断信息 | 正常、发现敏感字段、版本可更新 |
| 产品边界与隐私 | 能做与不做、数据分级、官方渠道说明 | 返回上一页 | 正常 |
| 403 | 非本机访问安全提示 | 关闭页面 | 非本机访问已阻止 |
| 404 | 找不到页面 | 返回总览 | 路由不存在 |

### 5.2 总览布局

按从需要关注到日常浏览的顺序排列：

1. **异常横幅**：仅在需要用户处理时出现，例如“本机浏览器未连接，2 个任务暂时无法检测”。
2. **今天需要关注**：即将放号、检测到有号、发送失败的通知，按时间排序。
3. **任务状态列表**：直接展示任务、最近结论、最近成功时间和下一次动作，不使用只有数字的 KPI 卡片。
4. **未来 7 天放号**：紧凑时间表，可进入规则日历。
5. **最近通知**：最多 5 条，带“查看全部”。

空状态不要展示全为 0 的统计卡片。

## 6. 创建关注任务向导

### 6.1 向导结构

桌面端为左侧步骤导航、右侧表单、底部固定操作区。移动端为顶部“第 2 步，共 5 步”和单列表单。每步自动保存非敏感草稿，刷新后可恢复。

步骤：

1. 就诊目标
2. 号别与医生
3. 日期与时段
4. 事件与通知
5. 确认并创建

底部按钮固定使用“上一步”“下一步”，最后一步改为“创建并开始监控”。按 Enter 不直接提交整份向导，避免日期选择器内误提交。

### 6.2 第 1 步：就诊目标

**字段顺序**

1. 医院
2. 院区
3. 科室

**真实文案**

- 页面标题：“选择就诊目标”
- 说明：“先选择医院、院区和科室。不同院区的放号规则可能不同。”
- 医院占位：“请选择医院”
- 院区占位：“请选择院区”
- 科室占位：“请选择科室”
- 搜索无结果：“没有找到匹配的医院。请检查名称，或查看当前支持范围。”
- 支持范围链接：“查看当前支持的医院”

**联动规则**

- 未选医院时，院区和科室禁用，并显示原因。
- 切换医院后清空不兼容的院区和科室。
- 每个医院选项可附“公开信息”“需本机浏览器”或“仅规则提醒”标签。
- C 级来源提示：“当前只能提供放号规则和定时提醒，暂不能检测实时号源变化。”

### 6.3 第 2 步：号别与医生

使用单选分段控件：

- 任意可用专家号
- 按职称
- 指定医生

**按职称**可选“主任医师”“副主任医师”“不限职称”。  
**指定医生**支持搜索并显示医生姓名、职称和院区。若来源没有稳定医生列表，允许输入姓名并标注“名称将在检测时匹配”。

**真实文案**

- 标题：“选择关注范围”
- 说明：“范围越宽，发现可用号源的机会越多，通知也可能更多。”
- 指定医生搜索：“输入医生姓名”
- 无匹配：“没有找到这位医生。你可以返回选择职称，或保留姓名进行匹配。”
- 校验：“请选择一种关注范围。”

### 6.4 第 3 步：日期与时段

**默认值**

- 日期：从明天开始的未来 7 天
- 最长范围：未来 14 天
- 时段：上午和下午均选中

**组件**

- 双月日期范围选择器，桌面端展示当前月和下月。
- 移动端使用单月日期选择加已选范围摘要。
- 时段复选框：“上午”“下午”。

**真实文案**

- 标题：“选择日期和时段”
- 说明：“最多关注未来 14 天。日期按北京时间计算。”
- 范围摘要：“2026 年 7 月 20 日到 7 月 26 日，共 7 天”
- 超出范围：“最多可选择连续 14 天。”
- 未选时段：“请至少选择一个时段。”
- 已过日期：“不能选择今天之前的日期。”

### 6.5 第 4 步：事件与通知

**事件类型及面向用户的名称**

| 技术事件 | 界面名称 | 解释 |
|---|---|---|
| `schedule_released` | 放号计划发布 | 官方页面出现新的排班或可预约日期 |
| `availability_changed_to_available` | 从无号变为有号 | 最近一次成功检测为无号，本次检测到可用 |
| `cancellation_slot_detected` | 发现退号 | 非常规放号时段出现新的可用号源 |

默认勾选“从无号变为有号”和“发现退号”。当存在已核验的常规放号规则时，额外默认开启“放号前 5 分钟提醒”。

**通知渠道**

- 已接入且已验证的渠道可勾选。
- 未配置时显示：“还没有可用的通知渠道。配置完成后会回到此处，你已填写的内容不会丢失。”
- 主动作：“配置通知渠道”
- 测试成功：“测试通知已发送，请在接收端确认。”
- 测试失败：“测试通知发送失败。请检查配置后重试。”

**频率说明**

“相同变化会自动去重，并在短时间内暂停重复提醒。你仍可在任务详情查看每次检测记录。”

MVP 不开放轮询频率和冷却时长的高级设置，避免引导高频查询。

### 6.6 第 5 步：确认并创建

按用户决策顺序展示摘要：

```text
北京同仁医院 · 崇文门院区 · 鼻科
任意可用专家号
2026 年 7 月 20 日至 7 月 26 日 · 上午
提醒：从无号变为有号、发现退号、放号前 5 分钟
来源：官方公开信息 · 最后核验于 2026 年 7 月 18 日 09:20
通知：已配置渠道名称
```

**边界确认**

“检测到变化后，你需要前往官方渠道，本人完成登录、验证码、实名确认和付款。本产品不会自动提交预约。”

**提交状态**

- 提交中：“正在创建关注任务…”
- 成功：“关注任务已创建”
- 成功补充：“首次检测将在合规间隔内开始。你可以离开此页面。”
- 失败：“任务没有创建成功。已保留你的设置，请稍后重试。”
- 冲突：“你已有一个条件相同的关注任务。”
- 冲突动作：“查看已有任务”“仍要创建不同任务”

### 6.7 向导校验与恢复

- 错误紧邻字段展示，页头同时出现可聚焦的错误摘要。
- 点击错误摘要中的项目，将焦点移到对应字段。
- 返回上一步不丢值。
- 刷新或登录超时后恢复草稿，并提示：“已恢复上次未完成的任务设置。”
- 来源能力在提交前发生变化时，不静默降级。展示差异并让用户确认，例如“实时号源检测暂不可用，此任务只能保留规则提醒”。

## 7. 规则日历

### 7.1 时间语义

规则日历默认以**放号发生时间**为时间轴。事件内必须同时写出对应的**可预约就诊日期**，避免用户把两者混淆。

示例：

```text
07:00 常规放号
北京同仁医院 · 鼻科
可预约 7 月 25 日门诊
可信度：高 · 7 月 18 日核验
```

所有时间使用北京时间。相对时间只能作为补充，例如“3 分钟后”，旁边仍保留绝对时间“10:30”。

### 7.2 默认视图与控制

- 默认视图：“未来 14 天”时间表。
- 可切换：“周”“列表”。
- 不提供月视图作为默认，因为 MVP 的关注范围不超过 14 天。
- 筛选：医院、院区、科室、可信度、是否需要重新确认。
- 快捷筛选：“只看我的关注”“只看需要确认”。
- 视图切换和筛选写入 URL，刷新与返回后保持状态。

### 7.3 桌面布局

1. 顶部筛选与视图切换。
2. 左侧固定日期和星期，右侧按时间排列事件。
3. 当前时间使用细线和“现在 10:32”文字标识。
4. 同时发生的事件纵向排列，不以重叠卡片隐藏内容。
5. 点击事件打开右侧详情面板，保留日历上下文和浏览器返回行为。

### 7.4 规则详情面板

必须包含：

- 医院、院区、科室
- 提前预约天数
- 常规放号时间
- 当日剩余号规则
- 可预约就诊日期计算结果
- 官方入口
- 信息来源名称与链接
- 最后核验时间
- 可信度及原因
- “需要重新确认”状态及原因
- 主动作“按此规则创建任务”

**可信度解释示例**

- 高：“来自医院官方页面，7 天内已核验。”
- 中：“来自医院官方说明，但最近一次核验已超过 30 天。”
- 低：“公开说明存在差异，建议前往官方渠道再次确认。”

### 7.5 日历状态

| 状态 | 文案 | 操作 |
|---|---|---|
| 首次空 | “未来 14 天还没有已记录的放号规则。” | 查看支持范围 |
| 筛选为空 | “当前筛选条件下没有规则。” | 清除筛选 |
| 加载 | “正在加载放号规则…” | 无 |
| 后台刷新 | 保留旧事件，页头显示“正在更新” | 无 |
| 部分失败 | “2 个来源暂时无法更新，其他规则仍可查看。” | 查看受影响来源 |
| 规则过期 | “这条规则超过 30 天未核验，时间可能已变化。” | 前往官方渠道确认 |
| 来源不可用 | “暂时无法读取这条规则的来源详情。” | 查看已保存的规则摘要 |

### 7.6 响应式变化

- 小于 768px 时自动切换为按日期分组的议程列表，不把 14 列压进窄屏。
- 详情面板在移动端变为全屏抽屉，并保留明确的“返回规则列表”。
- 筛选收进底部抽屉，入口显示已启用数量，例如“筛选 3”。

## 8. 监控详情

### 8.1 任务详情信息层级

**页头**

```text
北京同仁医院 · 崇文门院区 · 鼻科
未来 7 天 · 上午 · 任意可用专家号
状态：监控中
```

页头操作按优先级排列：

1. 有可执行官方入口时：“前往官方渠道查看”
2. “编辑任务”
3. 更多菜单：“暂停监控”“删除任务”

**首屏状态摘要**

- 当前结论：“无号”“检测到可用号源”或“当前结果未知”
- 最近检测：`2026-07-18 10:32:18`
- 最近成功：`2026-07-18 10:32:18`
- 下一次计划检测：`10:42 左右`
- 来源：`官方公开信息（A 级）`

数字和时间使用等宽数字，状态不使用只有颜色的圆点。

### 8.2 页面分区

1. **当前状态**：结论、时间、新鲜度和推荐动作。
2. **检测记录**：倒序时间线，可按“全部、变化、失败”筛选。
3. **关注条件**：医院、院区、科室、医生或职称、日期、时段和事件。
4. **通知记录**：发送、送达、失败、去重和冷却记录。
5. **来源与健康**：来源级别、最后成功、官方入口、适配器状态。

桌面端“检测记录”为主栏，“关注条件”和“来源与健康”为窄侧栏。移动端改为单列，当前状态优先，其余按上述顺序展开。

### 8.3 检测记录行

每条记录包含：

- 结果图标和文字
- 检测时间
- 可用性摘要
- 内容哈希变化说明
- 通知结果
- 可展开技术详情，不默认暴露原始响应或敏感信息

示例：

```text
10:32  无号变为有号
7 月 22 日上午发现 1 个可预约条目
已发送通知 · 查看详情
```

```text
10:22  检测失败
官方页面响应超时。上次成功结果为“无号”，时间 10:12
系统将在合规间隔后自动重试
```

### 8.4 当前结论状态

| 状态 | 标题 | 说明 | 主操作 |
|---|---|---|---|
| 首次检测中 | “正在等待首次检测” | “任务已创建，首次检测将在合规间隔内开始。” | 无 |
| 无号 | “最近一次检测未发现可用号源” | 显示检测时间，避免写“目前绝对无号” | 前往官方渠道查看 |
| 有号 | “检测到可用号源” | 显示日期、时段、医生或职称和检测时间 | 前往官方渠道查看 |
| 未知 | “当前结果未知” | 说明失败原因并保留上次成功结果 | 执行推荐恢复动作 |
| 已暂停 | “监控已暂停” | “暂停期间不会检测或发送通知。” | 恢复监控 |
| 已结束 | “关注日期已结束” | “所选日期范围已经过去。” | 复制为新任务 |
| 来源受限 | “当前只能提供规则提醒” | “该来源暂不能稳定检测实时号源。” | 查看放号规则 |

### 8.5 来源健康与恢复动作

| 原因 | 用户看到的说明 | 首选动作 |
|---|---|---|
| A 级页面超时 | “官方页面暂时没有响应，检测结果可能延迟。” | 等待自动恢复 |
| 被来源限流 | “为遵守访问频率限制，检测已暂缓。” | 查看下次检测时间 |
| 页面结构变化 | “官方页面内容发生变化，暂时无法确认号源状态。” | 查看来源状态 |
| B 级 Agent 离线 | “本机浏览器未连接，此任务暂时无法检测。” | 重新连接本机浏览器 |
| B 级会话失效 | “医院页面需要你在本机浏览器重新登录。” | 打开本机登录指引 |
| C 级来源 | “该来源只支持规则和定时提醒。” | 查看放号规则 |
| 通知失败 | “检测仍在运行，但通知没有发送成功。” | 修复通知渠道 |

恢复成功文案：“已恢复检测。最近成功时间为 10:46。”

### 8.6 合规的手动重试

- 正常运行时不显示高强调的“立即检测”。
- 失败状态下可显示“重新检查连接”或“重试一次”。
- 冷却中按钮禁用，并写明“10:42 后可重试”。
- 连续点击不得创建并发检测。
- 手动重试同样经过服务端频率限制和去重。

### 8.7 数据源状态页

数据源状态页回答“哪些来源现在能用、能做什么、影响哪些任务”，而不是只展示适配器技术名称。

**顶部摘要**

- `3 个来源正常`
- `1 个来源需要连接本机浏览器`
- `1 个来源仅支持规则提醒`
- 最近一次来源自检时间与“重新自检失败项”操作

**来源列表列定义**

| 列 | 内容 |
|---|---|
| 来源 | 医院或官方平台名称、来源级别 A/B/C |
| 当前能力 | 实时变化监控、规则提醒、定时提醒 |
| 状态 | 可检测、需要连接、仅规则、恢复中、暂不可用 |
| 最近成功 | 成功访问并解析的绝对时间 |
| 本机依赖 | 无、Playwright、本机浏览器会话 |
| 受影响任务 | 任务数量和可进入的任务列表 |
| 操作 | 唯一首选恢复动作和“查看详情” |

**状态文案**

- “可检测：官方公开信息可访问，最近成功于 10:32。”
- “需要连接：本机浏览器未连接，2 个任务暂时无法检测。”
- “仅规则：此来源当前不支持实时号源检测。”
- “恢复中：系统将在合规间隔后再次检查，预计 10:42。”
- “暂不可用：官方页面内容发生变化，当前结果未知。”

**自检规则**

- 首次配置、适配器更新后和用户主动修复后运行完整自检。日常只做轻量健康检查。
- “重新自检”默认只检查失败项，不同时并发访问全部医院来源。
- A 级检查可访问性与解析能力。B 级额外检查本机浏览器连接和会话是否可用。C 级只核验规则来源。
- 自检结果写入本机，诊断导出前自动移除 URL 参数、Cookie、Token、密钥和本机绝对路径中的用户名。

## 9. 通知体验

### 9.1 通知中心结构

顶部筛选：

- 未读
- 全部
- 发送失败

通知按日期分组。每条通知展示事件类型、任务、摘要、检测时间、渠道结果和官方入口。通知已读不等于已处理，用户可独立选择“标记为已处理”。

### 9.2 真实通知文案

**从无号变为有号**

```text
检测到可用号源
北京同仁医院 · 崇文门院区 · 鼻科
7 月 22 日上午发现可预约号源
检测时间：10:32:18
号源可能随时变化，请前往官方渠道确认。
[前往官方渠道查看]
```

**实验性 Browser Agent 明确看到可用状态**

```text
页面状态变为可用
北京协和医院 · 皮肤科
7 月 24 日下午的官方页面在用户主动读取时明确显示“可预约”
检测时间：14:08:42；状态可能随时变化
[前往官方渠道核验]
```

**放号前 5 分钟**

```text
还有 5 分钟到已记录的放号时间
北京同仁医院 · 崇文门院区 · 鼻科
预计 15:00 放号，目标就诊日期为 7 月 25 日
规则最后核验：7 月 18 日 09:20
[查看规则] [前往官方渠道]
```

**来源异常**

```text
监控需要处理
本机浏览器已断开，2 个关注任务暂时无法检测
最近成功检测：09:52
[重新连接]
```

### 9.3 去重和冷却的用户表达

- 相同任务、相同就诊日期和时段、相同事件、内容哈希未变化时，不重复发送。
- 冷却期间的新检测仍写入记录，通知状态显示“已抑制”。
- 状态从“有号”回到“无号”后再次变为“有号”，可视为新变化并重新通知。
- 用户可在通知详情看到：“相同变化已在 10:32 通知，本次未重复发送。”
- 不向用户开放会破坏来源访问频率的轮询设置。

### 9.4 前往官方渠道确认

首次打开某个来源时显示：

- 标题：“即将前往官方预约渠道”
- 正文：“接下来需要你本人完成登录、验证码、实名确认、医保选择和付款。本产品不会代你提交预约。”
- 来源：“北京同仁医院官方预约页面”
- 主按钮：“继续前往官方渠道”
- 次按钮：“留在当前页面”

外部页面在新标签页打开。链接旁带“在新标签页打开”无障碍文本。

### 9.5 渠道权限与失败

| 状态 | 文案 | 操作 |
|---|---|---|
| 未配置 | “还没有可用的通知渠道。” | 配置通知渠道 |
| 浏览器权限未询问 | “允许浏览器通知后，可在页面关闭时接收提醒。” | 允许通知 |
| 浏览器权限被拒 | “浏览器已阻止通知。请在网站设置中重新允许。” | 查看设置方法 |
| 渠道验证中 | “正在验证通知渠道…” | 无 |
| 已连接 | “通知渠道已连接，最近测试成功于 10:18。” | 发送测试通知 |
| 发送失败 | “通知发送失败，监控仍在继续。” | 查看原因并重试 |
| 凭证失效 | “通知渠道需要重新连接。” | 重新连接 |

### 9.6 通知渠道自检

通知渠道自检在首次配置、渠道保存后和发送失败后可运行。它不是只有一个“测试成功”的按钮，而是展示可诊断的四步结果：

1. **本地配置完整**：必填配置存在，密钥只显示末 4 位。
2. **外网可连接**：本机可访问通知服务。
3. **服务已接受**：通知服务返回可接受结果，显示响应时间和检查时间。
4. **用户已确认送达**：用户点击“我已收到测试通知”。若渠道支持可靠送达回执，可自动完成此步。

总状态：

- “自检通过”：四步均通过，最近通过时间可见。
- “等待确认”：服务已接受测试消息，但用户尚未确认收到。
- “自检失败”：明确失败步骤，监控任务可继续检测，但不得声称提醒可用。
- “权限被拒”：浏览器通知被阻止时，提供浏览器设置指引，不反复请求授权。

测试通知真实文案：

```text
北京挂号雷达测试通知
这是一条通知渠道自检消息，发送时间 10:18:24。
如果你看到这条消息，请回到本机管理端选择“我已收到测试通知”。
```

设置页主操作使用“保存并运行自检”。失败后保留已输入的非敏感配置，密钥是否保留取决于安全存储是否成功，不得在错误消息中回显完整密钥。

## 10. 错误恢复与全局反馈

### 10.1 错误消息结构

每个错误按以下顺序表达：

1. 发生了什么
2. 影响了什么
3. 系统保留了什么
4. 用户下一步做什么
5. 可展开的诊断编号和技术详情

示例：

```text
暂时无法更新号源状态
北京同仁医院来源响应超时。你的任务仍在监控，上次成功结果为“无号”，时间 10:12。
系统会在 10:42 左右自动重试。
[查看来源状态]
诊断编号：SRC-20260718-1042
```

### 10.2 常见故障与恢复

| 场景 | 页面行为 | 文案 | 恢复 |
|---|---|---|---|
| 外网断开 | 保留本机内容并暂停来源检查 | “无法连接外网，当前显示 10:32 保存在本机的内容。” | 网络恢复后自动检查失败项 |
| 本地后台不可用 | 显示全页错误，不伪装为空 | “本地服务暂时没有响应。你的任务和历史记录仍保存在本机。” | 运行本机自检 |
| 部分来源失败 | 正常内容继续显示，受影响区域标记 | “2 个来源暂时无法更新。” | 查看受影响来源 |
| 本地数据目录不可写 | 停止新增记录，不删除旧数据 | “无法写入本地数据目录，新的检测记录暂未保存。” | 查看目录权限指引 |
| 403 | 不加载任何本地数据 | “此开源版仅允许本机访问。请在运行本服务的电脑上打开管理端。” | 关闭页面 |
| 404 | 品牌化 404 | “没有找到这个页面，链接可能已失效。” | 返回总览 |
| 数据提交冲突 | 不覆盖较新版本 | “这项任务刚刚在其他页面更新。” | 查看最新内容，再次编辑 |
| 来源限流 | 不允许连续重试 | “检测已按访问频率限制暂缓。” | 显示下一次允许时间 |
| Agent 离线 | 任务结论显示未知 | “本机浏览器未连接。” | 重新连接 |
| Agent 登录失效 | 不要求上传凭证 | “请在本机浏览器完成医院页面登录。” | 打开本机操作指引 |
| 页面结构变化 | 停止输出有号或无号结论 | “官方页面内容发生变化，暂时无法确认状态。” | 等待适配器修复或查看官方入口 |
| 通知发送失败 | 检测与通知状态分离 | “检测成功，但通知未发送。” | 重试通知或修复渠道 |

### 10.3 反馈组件使用规则

- **页面横幅**：跨区域且需要处理的问题。
- **内联错误**：字段或局部加载失败。
- **Toast**：保存成功、复制完成、撤销入口等短暂反馈，不承载唯一错误信息。
- **确认对话框**：仅用于删除、清理历史等不可忽略的高风险动作。
- **详情抽屉**：规则详情、通知详情、诊断详情，保留当前列表上下文。
- **专用页面**：创建向导、任务详情和复杂来源恢复，不能用模态框硬塞。

## 11. 空、加载、失败与权限状态规范

### 11.1 空状态

空状态必须在请求成功且结果确实为空后出现。结构为“发生原因 + 可执行下一步”，不使用装饰性插画占据首屏。

| 场景 | 标题 | 正文 | 操作 |
|---|---|---|---|
| 无任务 | “还没有关注任务” | “创建任务后，我们会按条件监控放号和退号变化。” | 创建关注任务 |
| 筛选无任务 | “没有符合条件的任务” | “尝试调整状态、医院或科室筛选。” | 清除筛选 |
| 无规则 | “未来 14 天还没有已记录的规则” | “你仍可创建号源变化监控，或稍后查看。” | 创建关注任务 |
| 无通知 | “还没有通知” | “检测到符合条件的变化后，通知会出现在这里。” | 查看关注任务 |
| 无失败 | “当前没有需要处理的问题” | “所有已启用来源均在正常工作。” | 返回总览 |
| 搜索无结果 | “没有找到匹配内容” | “检查关键词，或清除筛选后重试。” | 清除筛选 |

### 11.2 加载状态

- 首次加载使用与真实布局相同的骨架，不显示最终空状态。
- 骨架最多持续可见 10 秒，超过后转为明确的慢加载提示。
- 后台刷新保留现有内容，顶部显示“正在更新”，不得闪成空页面。
- 按钮提交后保持原宽度，文字改为“正在保存…”并显示进度图标，防止布局跳动。
- 屏幕阅读器通过礼貌级 live region 获知“正在加载”和“加载完成”，不逐行播报骨架。

### 11.3 失败状态

- 全页失败和局部失败视觉层级不同。
- 若有缓存，展示“上次成功内容”和明确时间。
- 失败时不把历史有号状态继续当作当前结论。
- 技术错误默认折叠，诊断编号可复制。
- 重试按钮必须有节流，执行中不可重复提交。

### 11.4 权限状态

稳定开源版不设置团队 RBAC。权限状态主要来自本机访问边界、操作系统目录权限、浏览器通知、本机 Agent 和来源数据级别，不能全部写成“没有权限”。

| 类型 | 状态表达 | 不应出现 |
|---|---|---|
| 非本机访问 | “此开源版仅允许本机访问。” | 登录框、空白页或继续加载本地数据 |
| 本地数据目录 | “无法写入本地数据目录，请检查目录权限。” | 要求开放整个磁盘权限 |
| 浏览器通知 | “浏览器已阻止通知，请在网站设置中重新允许。” | 反复弹系统授权提示 |
| B 级来源 | “需要连接本机浏览器，脱敏结果只写入本机。” | 要求上传 Cookie、Token 或账号密码 |
| C 级来源 | “该来源只支持规则和定时提醒。” | 可点击的实时监控开关 |
| 官方入口登录 | “请在官方页面本人完成登录。” | 内嵌医院账号密码表单 |

## 12. 响应式规范

响应式用于窄窗口、系统缩放和未来兼容，不改变“仅本机访问”的安全默认。手机收到的外部通知必须自包含医院、科室、时间和官方入口，不能依赖手机打开本机管理端才能理解。

### 12.1 目标视口

| 视口 | 布局策略 |
|---|---|
| 1440px 及以上 | 240px 固定侧栏，主内容最大宽度 1280px，详情页可双栏 |
| 1024px 至 1439px | 208px 紧凑侧栏，减少列间距，保留桌面表格 |
| 768px 至 1023px | 64px 图标侧栏或可收起导航，次要筛选进入抽屉 |
| 375px 至 767px | 顶部栏加导航抽屉，单列内容，表格转换为信息行或卡片列表 |
| 320px 至 374px | 保持关键操作完整可见，按钮文字不得截断 |

### 12.2 组件转换

- **任务表格**：移动端转为列表行，固定展示任务名、状态、最近成功时间和主操作，其余信息展开查看。
- **规则日历**：移动端默认议程列表，不横向压缩多日网格。
- **向导**：移动端单列，底部操作区考虑 `safe-area-inset-bottom`。
- **任务详情**：双栏转单列，检测记录优先于配置详情。
- **筛选**：桌面内联，移动端抽屉，关闭后在入口显示已启用筛选数量。
- **通知**：主操作保持自然宽度并左对齐，不强制铺满整行。
- **对话框**：窄屏使用接近全屏的底部抽屉，破坏性确认仍需清楚的标题和后果说明。

### 12.3 内容适配

- 医院、院区、科室名称最多两行，不能仅靠省略号隐藏关键院区。
- 日期优先使用完整中文格式，空间不足时缩为“7 月 22 日 上午”，不截断为不可理解的片段。
- 状态行允许换行，状态标签本身不拆字。
- 在 1280px、375px 和 320px 下验证中文按钮、表格、日期选择器和错误摘要。

## 13. 无障碍要求

以 WCAG 2.2 AA 为验收基线。

### 13.1 键盘与焦点

- 文档第一个可聚焦元素为“跳到主要内容”。
- 所有操作可用键盘完成，导航使用链接，动作使用按钮。
- 焦点顺序与视觉顺序一致，打开抽屉或对话框后焦点进入容器，关闭后回到触发按钮。
- 可见焦点环与背景对比清楚，不能只依赖浏览器默认且不能移除后无替代。
- 任务表格支持按 Tab 进入行内操作，不把整行和内部按钮做成冲突的嵌套点击区。
- 向导步骤可返回，但不能让用户跳过尚未通过校验的必填步骤。

### 13.2 语义与屏幕阅读器

- 页面只有一个主标题，标题层级连续。
- 主导航使用 `nav`，主内容使用 `main`，状态区使用有名称的 `section`。
- 图标按钮提供明确的 `aria-label`，例如“暂停北京同仁医院鼻科监控”。
- 状态更新使用 `aria-live="polite"`，高风险失败才使用 `assertive`。
- 错误摘要聚焦后，逐项链接到对应字段。字段使用 `aria-describedby` 关联帮助和错误。
- 外部官方链接说明“在新标签页打开”。
- 装饰图标隐藏于辅助技术，状态图标必须有文字等价物。

### 13.3 日历与时间线

- 日历网格使用正确的日期语义，方向键在日期间移动，Enter 或 Space 选择。
- 每个规则事件的无障碍名称应完整，例如：“7 月 18 日 7 点，北京同仁医院鼻科常规放号，可预约 7 月 25 日门诊，可信度高”。
- 提供与日历信息等价的列表视图，不能要求屏幕阅读器用户解析二维视觉位置。
- 当前时间线不只用一条彩线表示，附“当前时间”文本。

### 13.4 颜色、字体与动效

- 正文和背景对比度至少 4.5:1，大文本至少 3:1，控件边界和焦点至少 3:1。
- 状态同时使用图标、文字和颜色。
- 中文正文默认至少 14px，主要阅读内容建议 15 至 16px，行高 1.7 左右。
- 支持浏览器放大至 200%，不丢信息或操作。
- 遵循 `prefers-reduced-motion`。状态切换只使用短暂的透明度或位移动效，不使用弹跳。
- 所有交互目标至少 40×40px，移动端关键目标建议 44×44px。

### 13.5 表单与认证

- 必填项使用文字“必填”或语义属性，不只用星号。
- 输入错误在字段旁说明如何修复，不能只在页顶说“提交失败”。
- 不设置过短的会话倒计时。会话将过期时提前提醒，并保存非敏感草稿。
- 不要求认知测试式验证。若官方渠道需要验证码，应明确该步骤发生在官方页面，不在本产品中模拟。

## 14. 中文文案语气与词汇表

### 14.1 语气

- 准确、冷静、可执行。
- 不制造“抢号”焦虑，不夸大检测能力。
- 成功状态不使用感叹号。
- 错误不使用“糟糕”“出错啦”等轻佻表达。
- 先说影响，再给行动，技术细节放到展开区域。

### 14.2 统一词汇

| 使用 | 不使用 | 原因 |
|---|---|---|
| 关注任务 | 抢号任务 | 产品不自动抢号 |
| 检测到可用号源 | 抢到号、锁定号源 | 只能证明检测时页面可用 |
| 前往官方渠道查看 | 立即预约 | 本产品不提交预约 |
| 最近成功检测 | 最后刷新 | 区分失败检测与成功检测 |
| 当前结果未知 | 暂时无号 | 失败不等于无号 |
| 发现新的可用号源 | 捡漏成功 | 避免夸大和情绪化表达 |
| 本机浏览器 | 浏览器节点 | 面向非技术用户 |
| 信息来源 | 数据抓取源 | 强调官方出处而非采集技术 |
| 需要重新确认 | 失效 | 规则可能仍正确，只是过期未核验 |

## 15. OpenDesign 可直接使用的原型 brief

以下内容可整体粘贴给 OpenDesign。原型以中文高保真可点击桌面 Web 为主，同时包含关键移动端适配。

```text
项目名称：北京挂号雷达

产品定义：
设计一个稳定开源、仅本机运行、明确不使用 Docker 的桌面优先响应式 Web 管理端，用于展示首批医院放号规则、创建关注任务、低频识别协和公开页面的新排班发布并发送提醒。它不是自动抢号器，不自动提交预约，不绕过验证码和风控，不保存身份证、医保卡、医院账号密码、Cookie 或 Token。检测到变化后，只引导用户前往官方渠道，由用户本人完成后续操作。

目标用户与使用情境：
个人用户在运行服务的电脑上配置和检查关注任务。外部通知在手机上必须自包含关键信息并可直接打开官方入口，不依赖手机访问本机管理端。响应式移动画板用于验证窄窗口和未来兼容，不得暗示默认开放局域网或公网访问。用户关心医院、院区、科室、医生或职称、未来 7 至 14 天、上午或下午，以及监控是否仍然可靠。用户不应被迫理解适配器或内容哈希等技术术语。

运行与安全边界：
1. 默认只允许 localhost 或等价本机回环访问，非本机访问显示安全阻止页，不显示本地数据。
2. 首次配置依次完成开源版安全确认、本机服务自检、数据源自检和通知渠道自检。
3. 本机服务自检包含 Web/API、SQLite、持久任务 Worker、本地数据目录、真实通知渠道和可选 Browser Agent 配对；不检查或依赖 PostgreSQL、Redis。
4. 不出现 Docker、Docker Compose、容器、镜像、NAS、云服务器、反向代理或公网部署入口。
5. 通知密钥只在本机保存且掩码显示。诊断导出自动移除密钥、Cookie、Token、URL 参数和用户目录名称。
6. 开源版与社区适配器不代表医院官方认可，所有结论需要在官方渠道确认。

对标产品的具体借鉴：
1. Linear：借鉴紧凑的左侧导航、清楚的行状态和键盘可达操作，不复制其品牌与深色主题。
2. Sentry：借鉴“当前健康状态 + 事件时间线 + 明确恢复动作”的监控详情结构。
3. Google Calendar：借鉴清楚的时间轴、当天定位和日历到议程列表的响应式转换，同时显式区分放号时间与就诊日期。

视觉论点：
“临床信息台”，明亮、精确、克制、可信。界面像一张持续更新的值班信息台，不像营销首页，也不像刺激抢购的秒杀工具。高密度但不拥挤，主要依靠排版、细分隔线、状态点和时间对齐建立层级，不使用装饰渐变、玻璃拟态或大面积阴影卡片。

内容计划：
采用工具型应用壳。先让用户定位当前健康和待处理事项，再显示任务与时间状态，最后提供官方出口与诊断细节。没有 hero，没有宣传口号，没有虚假的 KPI 大数字。

交互论点：
1. 所有按钮按下时轻微缩放到 0.96，持续约 120ms，可被中断。
2. 详情抽屉以 180ms ease-out 滑入并淡入，减少动态模式下仅淡入。
3. 状态变化用图标 120ms 交叉淡化，不旋转、不弹跳。

主题与色彩：
只做浅色 MVP。使用 OKLCH 作为设计 token 源，括号内为 hex 参考。
- canvas：oklch(0.977 0.003 174.5)，#F5F8F7，主画布
- sidebar：oklch(0.955 0.009 179.6)，#EAF2F0，侧栏和次级表面
- surface：oklch(1 0 0)，#FFFFFF，表单与浮层
- text-primary：oklch(0.251 0.020 185)，#172523
- text-secondary：oklch(0.526 0.022 184.3)，#5D6F6C

- accent：oklch(0.511 0.086 186.4)，#0F766E，主按钮与选中状态
- accent-hover：oklch(0.445 0.075 187.3)，#0B615B
- success：oklch(0.514 0.100 167.1)，#13795B
- warning：oklch(0.502 0.108 70.5)，#8A5700

- info：oklch(0.484 0.133 253.9)，#1D5FA7
- focus：oklch(0.560 0.150 250.2)，#1677C8
每种状态都必须有图标和中文文字，不能只使用颜色。输出前验证 WCAG 2.2 AA 对比度。

字体与排版：
不引入装饰性展示字体。采用系统中文 UI 字体栈：-apple-system, BlinkMacSystemFont, "SF Pro Text", "PingFang SC", "Microsoft YaHei", "Noto Sans CJK SC", sans-serif。原因是这是高频扫描的中文工具界面，需要稳定字形、数字和低加载成本。

- 辅助文字 13px / 400 / 1.5
- 时间、数量与表格数字使用 tabular-nums
- 中文不设置负字距

布局与尺寸：
- 1440px 桌面画板，240px 左侧栏，主内容最大宽度 1280px
- 1024px 画板使用 208px 侧栏

应用壳：
左侧主导航依次为“总览、关注任务、规则日历、监控状态、通知、设置”。底部固定显示“本机运行”、系统状态和“开源版与安全”。主区页头有页面标题、简短说明和一个关键操作。全局异常只在需要用户处理时显示横幅。
```

## 16. 原型验收清单

- [ ] 首次配置明确说明稳定开源、仅本机运行、不使用 Docker，并阻止非本机访问。
- [ ] 本机 Web/API、SQLite、Worker、数据目录、真实通知渠道和可选 Browser Agent 配对都有独立自检状态和恢复动作。
- [ ] 通知渠道只有在配置、连通、服务接受和送达确认完成后才显示“自检通过”。
- [ ] 数据源状态同时展示 A/B/C 能力、最近成功、本机依赖、受影响任务和首选恢复动作。
- [ ] 诊断导出和开源问题反馈不会泄露密钥、Cookie、Token、URL 参数或用户目录名称。
- [ ] 用户能从空状态在不输入任何敏感信息的前提下完成任务创建。
- [ ] A、B、C 级来源的能力差异在选择目标和确认步骤都清楚可见。
- [ ] 任一检测失败都不会显示为“无号”。
- [ ] 任一有号提醒都包含检测时间、号源摘要、官方入口和变化可能过期的提示。
- [ ] 规则日历明确区分放号时间与可预约就诊日期。
- [ ] 任务详情同时展示最近检测与最近成功。
- [ ] 异常状态保留最后成功内容和时间，并提供唯一首选恢复动作。
- [ ] 加载过程不闪现空状态，后台刷新不清空旧内容。
- [ ] 375px 下关键流程可完成，320px 下按钮文案不截断。
- [ ] 键盘可完成创建任务、打开规则详情、处理通知和恢复监控。
- [ ] 所有状态都具有文字等价物，颜色对比满足 WCAG 2.2 AA。
- [ ] 原型中没有任何自动预约、验证码绕过、账号凭证上传或高频轮询暗示。
