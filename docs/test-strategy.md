# 北京挂号雷达 · 测试与验收策略

> 依据：`docs/source-requirements.md`、`docs/PRD.md` 及后续用户决策  
> 决策基线：稳定开源版；仅本机运行；Node.js 单进程；`better-sqlite3` 磁盘 SQLite 持久化；进程内 Durable Job Runner；按需启动真实 Playwright；安装与运行不依赖外部基础设施服务。

## 1. 目标与“真实可用”定义

### 1.1 MVP 必须证明的能力

1. 从选定的官方来源读取并规范化号源或放号规则，来源、检测时间、最后成功时间和失败原因可追溯。
2. 正确保存和匹配关注任务，并识别：
   - `schedule_released`
   - `availability_changed_to_available`
   - `cancellation_slot_detected`
3. 在放号前 5 分钟或状态有效变化后，通过至少一个真实通知渠道送达消息。
4. SQLite 中的持久 Job、事件、通知投递和去重状态能经受进程退出、重启和重复执行，不依赖内存定时器保存事实。
5. 来源失败时显示 `unknown`/来源异常，不把失败、登录墙或空响应误报为“无号”。
6. 用户只会被引导到官方渠道；应用不登录、不提交预约、不处理验证码、实名、医保或付款。
7. 未参与开发的验收者从全新 clone 开始，仅准备 `.nvmrc` 指定的 Node.js 与 npm，即可执行 `npm ci`、迁移、`npm start` 和 smoke；无需安装或启动数据库、缓存、队列等服务。
8. SQLite、备份、日志、诊断导出、浏览器产物和 GitHub CI artifacts 中不存在医院会话凭据或敏感身份信息。

### 1.2 证据等级

| 等级 | 证据 | 能证明什么 |
| --- | --- | --- |
| E0 | 手写数据、stub、mock server、capture notifier | 只证明局部开发行为，不参与最终“真实可用”结论 |
| E1 | 脱敏后的真实官方响应/页面，经生产 Adapter 和完整本地栈回放 | 证明真实格式解析、状态变化、持久任务和通知链路可重复 |
| E2 | 生产 Adapter 低频访问 live 官方来源，且同一时刻人工比对一致 | 证明当前来源可达、语义解释正确 |
| E3 | 自然发生的官方状态变化，经真实调度、SQLite、进程内 Job Runner 到达真实通知账号 | 证明现场闭环 |

MVP 发布至少要求全部 E1、E2 和真实渠道送达通过。只有 E3 通过后才能声称“状态变化提醒已完成现场闭环”。观察期内没有自然变化时，可用真实历史变化 fixture 走完整生产链，并把消息明确标成“验收测试”；此时只能记为“条件通过：现场变化闭环待证”，不能把回放伪装成 E3。

### 1.3 不允许用 mock 替代的发布证据

- HTTP 集成测试必须监听真实 loopback 端口并发送真实 HTTP 请求，不能只调用 handler。
- 数据库集成必须使用生产依赖 `better-sqlite3` 打开的真实磁盘文件，不能用对象仓库、其他 SQLite 驱动或 `:memory:` 代替。
- Durable Job Runner 必须运行生产领取、状态转换、重试和恢复逻辑，不能在测试中改成直接函数调用。
- UI E2E 必须启动真实 Chromium 和真实本地应用。
- live 验收禁止替换官方来源；通知送达验收禁止以控制台输出或 capture endpoint 代替真实账号/设备。
- fixture 回放是 E1，不是 live 证据；CI 绿色也不能替代本机 live 与真实送达。

## 2. 测试金字塔与执行节奏

| 层级 | 建议占比 | 范围 | 时机 |
| --- | ---: | --- | --- |
| 静态检查与单元/领域测试 | 55%～65% | 校验、匹配、状态机、时间、去重键、脱敏、规范化和哈希 | 每次提交 |
| 契约/组件测试 | 15%～20% | HTTP schema、Adapter、通知 payload、migration checksum | 每次提交 |
| 真实本地集成测试 | 15%～20% | HTTP + 磁盘 SQLite + Durable Job Runner + Playwright | 每次 PR |
| Playwright E2E 与全新 clone smoke | 5%～10% | 用户流程、进程重启、安装/迁移/启动 | 每次 PR / RC |
| live、真实送达与故障演练 | 数量少但强制 | 官方来源、真实渠道、恢复与观察期 | RC / 发布前 |

测试标签统一为 `unit`、`contract`、`integration`、`e2e`、`smoke`、`live`、`destructive`。普通 fork/PR CI 不获得真实通知密钥，不运行 `live` 或 `destructive`；这些门禁在隔离的本机 RC 环境执行并归档。

## 3. 测试数据与环境

### 3.1 数据集

1. **合成领域样本**：覆盖筛选和边界，不含真人数据。
2. **真实来源 fixture**：从官方公开来源采集后最小化、脱敏；记录官方域名、采集时间、Adapter 版本、原始/规范化内容哈希和脱敏说明。
3. **真实变化序列**：至少覆盖“未发布→已发布”“无号→有号”“有号→无号→再次有号”和“仅噪声变化”。
4. **恶意输入**：脚本、SQL 片段、超长 Unicode、恶意重定向、内网 URL、日志换行。
5. **隐私金丝雀**：明显虚构且可全仓检索的 Cookie、Token、账号、身份证号和医保卡号。

fixture 禁止保存完整请求头、`Cookie`、`Set-Cookie`、`Authorization`、会话 ID、用户标识、浏览器 profile、完整 Trace 或带敏感查询参数的 URL。为解析保留的字段必须使用不可逆替代值。

### 3.2 环境

| 环境 | 数据库与任务执行 | 来源 | 通知 | 用途 |
| --- | --- | --- | --- | --- |
| 本地快速测试 | 临时磁盘 SQLite + 生产 Job Runner | 合成/fixture | capture channel | 快速反馈 |
| GitHub PR CI | 临时磁盘 SQLite + 生产 Job Runner | fixture server | capture channel | 契约、集成、E2E |
| RC 全新 clone 本机 | 新数据目录 + 正式迁移 + 生产 Job Runner | fixture + live | 真实测试账号 | smoke、live、真实送达 |
| 本机现场观察 | 生产形态数据目录 | live | 真实账号/设备 | E3 与稳定性 |

所有产品时间以 `Asia/Shanghai` 展示，存储格式必须无歧义。测试同时覆盖 UTC 序列化、跨日、月末、年末、闰日、进程 `TZ` 错误和系统时钟小幅漂移。

## 4. 关键领域测试

### 4.1 放号规则

- 规则完整包含医院、院区、科室、提前预约天数、常规放号时间、当日剩余号规则、官方入口、信息来源、最后核验时间、可信度和是否需重新确认。
- 最后核验时间只因成功人工核验推进；来源检测失败不能冒充规则已核验。
- 30 天/90 天过期与可信度边界按 PRD 固定时间测试。
- 官方入口只接受批准的 `https` 官方域名；拒绝短链、用户信息 URL、非 Web scheme、loopback、私网和云元数据地址。
- 同名医院院区、科室和医生不能错误合并。

### 4.2 关注任务与匹配

参数化覆盖：

- 北京同仁医院崇文门院区鼻科；
- 北京协和医院或北京大学第一医院皮肤科的最终选定目标；
- 指定医生、指定职称、任意可用专家号；
- 未来第 7 天、第 14 天及日期端点；
- 上午、下午、全天和院区偏好；
- 三种事件类型；
- 创建、编辑、启停、删除及重启后恢复。

关键断言：空医生条件表示“不限定医生”，职称只按明确映射匹配，日期范围端点语义与 API schema 一致；停用/删除/编辑后的已到期 Job 执行前会再次检查任务版本和启用状态；多个任务复用来源检查但不串通知冷却状态。

### 4.3 状态机、快照与事件

至少区分 `unknown`、`unavailable`、`available` 和来源支持时的 `not_released`。空结果不能同时表示请求失败与合法无号。

| 前态 | 新状态 | 预期 |
| --- | --- | --- |
| 无历史 | 任意明确状态 | 建立基线，不产生变化事件 |
| `unavailable` | `available` | 一次 `availability_changed_to_available` |
| 已发布排班近期 `unavailable` | `available` | 符合窗口时产生 `cancellation_slot_detected`，文案为“疑似退号回流” |
| 未出现排班 | 首次出现未来排班 | 一次 `schedule_released` |
| `available` | 同语义 `available` | 不产生事件 |
| 任意明确状态 | `unknown` | 保留最后明确状态，不产生号源事件 |
| `unknown` | 恢复为最后明确状态 | 只恢复健康，不产生假变化 |

内容哈希必须忽略无关空白、字段顺序和动态追踪参数，同时能识别医生、日期、午别、号别、可用性及官方入口的语义变化。相同规范化快照重复持久化时，不得重复生成事件。

### 4.4 调度、去重与冷却

- 放号时刻前 `5:00` 触发；`5:01` 不提前，`4:59` 不漏发，允许误差按 PRD 为 ±30 秒。
- 持久 Job 在应用退出、重启、电脑休眠恢复和 planner 重扫后仍可恢复，不因内存 timer 丢失。
- 去重键稳定覆盖任务、事件类型、号源键和状态序列；无关内容变化不改变去重结果。
- 同一 Job 被重复领取或重试时，领域事件和通知记录仍唯一。
- 60 秒冷却内的不同事件聚合而非丢弃；新一轮“无号→有号”可再次提醒。
- 多任务命中同一查询时只访问上游一次；同一来源并发为 1，最短访问间隔和退避不能被普通配置绕过。
- 停机空窗恢复后先建立新基线，不推断离线期间发生过变化；过期提醒按产品规则标记 missed，不伪装准时送达。

## 5. HTTP API + `better-sqlite3` 磁盘 SQLite + Durable Job Runner + Playwright 集成测试

本节是架构主 seam。每个 PR 都必须运行真实 loopback HTTP、真实磁盘 SQLite、同一 Node.js 主进程内的生产 Job Runner 和真实 Playwright Chromium。

### 5.1 HTTP API + 真实 `better-sqlite3`

- 从空文件执行全部正式 migration；重复执行幂等，已发布 migration checksum 被改动时启动失败。
- HTTP 通过随机 loopback 端口访问，覆盖规则、关注任务、快照、事件、Job、通知结果和健康状态。
- CRUD 的状态码、错误 schema、字段校验与 SQLite `FOREIGN KEY`、`CHECK`、唯一索引一致。
- API 成功响应后立即关闭进程并重新打开同一数据库，数据仍存在，证明不是内存状态。
- 状态更新、领域事件、通知批次和后续 Job 在同一事务边界内保持原子性；任一注入点失败均无半条事件。
- 两个真实 `better-sqlite3` 连接指向同一磁盘文件并制造写锁竞争，验证 `busy_timeout`、有界重试和可操作错误；不得无限卡住 HTTP，也不得静默丢写。
- 启用并验证 `foreign_keys`、预期 journal/synchronous 配置及启动时 `integrity_check`。
- 列表分页、排序、并发 HTTP 写入和多标签页版本冲突不漏项、不重复、不覆盖较新修改。
- 所有测试数据库位于独立临时目录；测试结束关闭句柄并删除数据库、WAL/SHM 和备份。

### 5.2 进程内 Durable Job Runner

- API 创建/编辑关注任务后，正式 planner 将持久 Job 写入同一 SQLite；测试不得手工调用领域函数伪造完成。
- Runner 从数据库领取到期 Job，持久记录 `pending/running/succeeded/failed`、尝试次数、下次执行时间和脱敏错误码。
- 领取和状态更新使用真实事务；重复 planner 扫描产生相同去重键时只保留一个 Job。
- 延迟 Job 在目标时间前不执行，到时后在 ±30 秒内执行；另有真实时钟测试，不只依赖 fake clock。
- 在“Job 已持久化未领取、已标记 running、事件事务提交后、通知调用前”发送 `SIGTERM`，随后重启同一应用和数据目录：Job 最终完成或进入可见终态，事件不丢失、不重复。
- `SIGTERM` 后停止领取新 Job，在宽限期内完成或安全释放当前工作，关闭 SQLite 和 Browser；退出码和运行会话状态正确。
- 启动时恢复过期的 `running` Job；对外部通知结果不确定的记录不得盲目重发。
- 第二个 `npm start` 指向同一数据目录时，在任何来源请求前安全失败并提示已有实例。
- Runner 异常不应让 HTTP 健康页继续显示“全部正常”；来源失败则只降级对应 Adapter，不把整个应用伪装停止。

### 5.3 真实 Playwright

- E2E 使用真实 Chromium 打开 loopback UI，不替换 `page`、不调用前端内部 store。
- 需要浏览器渲染的 A 级 Adapter 使用生产 Playwright 路径和临时无登录 Context，验证目标内容、超时和正常关闭。
- 页面崩溃、重定向循环、下载弹窗、选择器失效和 DOM 变化返回结构化失败，不变成空号源。
- Context 间隔离；任务结束、进程退出和测试清理后，不残留 Cookie、storage state、profile、截图或 Trace。
- 网络路由只允许 Adapter manifest 中的官方域名和必要静态资源；阻止 loopback 回打、私网、云元数据和任意用户 URL。
- E2E 失败产物必须先过隐私扫描再上传 CI。

### 5.4 完整 E1 闭环

1. 通过真实 HTTP API 创建关注任务；
2. planner 把检测 Job 持久化到真实 SQLite；
3. 进程内 Runner 领取 Job 并调用生产 `SourceAdapter`；
4. Adapter 回放脱敏的真实变化 fixture；
5. 同一数据库事务保存快照、状态、领域事件和通知批次；
6. Runner 调用通知 Channel，保存投递结果与下一步；
7. Playwright UI 展示相同的检测时间、事件、健康和通知状态；
8. 重启整个 Node.js 进程，重复相同输入，确认没有重复事件或通知。

这证明生产组件可协作，但仍只算 E1；RC 必须另跑 live 与真实送达。

## 6. 通知契约与重试测试

### 6.1 领域消息

通知必须包含事件类型、医院、院区、科室、日期/午别、医生或职称、检测时间、号源摘要、来源状态、官方入口和“以官方页面为准/不代替人工预约”的边界说明。验收测试消息必须显著标记，不能冒充真实放号。

使用 schema 与 golden message 双重测试：字段缺失、错误时区、未知写成有号、官方链接越界、供应商长度截断导致关键上下文丢失均应失败。稳定 Message-ID/投递键不得包含患者身份数据。

### 6.2 渠道契约与持久重试

- 覆盖成功、400/401/403、429、5xx、DNS/连接超时和响应中断。
- 可重试错误按 1、5、15 分钟持久化重试，最多 3 次；最终失败在 UI 可见，不无限重试。
- 明确在发送前失败可以重试；发送过程中断、无法判断渠道是否已接受时标记 `delivery_unknown`，不得因进程重启自动轰炸用户。
- 同一投递记录被重复执行时，稳定 Message-ID、数据库唯一约束和状态机共同抑制重复。
- PR 用 capture channel 检查协议；RC 必须向真实账号/设备发送，并记录收到时间、脱敏渠道 ID、消息截图和官方链接。应用返回成功但用户未收到不算送达。
- 若渠道有回执 webhook，验证签名、时间窗、防重放；本地产品不应为接收回执而要求公网暴露管理端。

## 7. `SourceAdapter` fixture、回放与 live canary

### 7.1 统一契约

每个 Adapter 必须声明 A/B/C 等级、官方域名、支持范围、transport、最小访问间隔和可产生的事件。输出必须区分有号、无号、未发布和未知，并包含检测时间、规范化排班、官方入口、内容哈希与结构化失败码。

C 级来源只提供规则和定时提醒，明确标记“未监控实时号源”；不得为通过契约而伪造可用性。P0 的 A 级 Playwright Context 不携带医院登录态。

### 7.2 fixture 回放

每个首批 Adapter 至少有：正常有号、正常无号、未发布、多医生/日期/午别、合法空结果、字段缺失、维护页、登录墙、验证码页、403、429、5xx、超时、DOM/JSON 噪声变化和一组真实状态变化序列。

fixture 更新必须人工 review 规范化 diff。解析失败时不得无条件更新 golden；先确认官方语义。原始与规范化哈希分开记录，以区分来源漂移、脱敏修改和 parser 修改。

### 7.3 live canary

- 仅访问批准的官方公开入口，使用生产 Adapter 与生产网络路径。
- 串行、低频，不使用代理、账号轮换或验证码绕过；失败不得自动提高频率。
- 断言“可访问且可解释为受支持状态”，不要求当前一定有号。
- 验收人同一时刻人工查看官方页面，抽样比对医院、院区、科室、日期、午别和状态。
- 记录时间、结果分类、规范化摘要、内容哈希、Adapter 版本和人工结论；不保存完整页面或会话材料。

## 8. Playwright E2E

### 8.1 每个 PR 的可重复 E2E

使用真实本地应用、磁盘 SQLite、生产 Runner、真实 Chromium和 E1 回放：

1. 查看规则来源、核验时间、可信度和官方入口。
2. 创建同仁崇文门鼻科任务，配置医生/职称、日期、午别和事件。
3. 编辑、停用、启用并刷新，证明状态来自 SQLite。
4. 回放“无号→有号”，观察事件、健康与通知状态。
5. 重放同一响应并重启整个应用，确认只有一条事件/投递。
6. 回放来源超时，确认 UI 显示 `unknown`、失败原因和最后成功时间，不显示无号。
7. 删除任务后继续运行到期 Job，确认 Runner 因任务版本/状态不再通知。
8. 点击官方入口，验证新页面属于批准域名；到此停止，不进行登录、验证码、预约确认或付款。

同时覆盖最终选定的皮肤科目标。Trace、截图和视频只在失败时保留，上传前执行隐私扫描。

### 8.2 RC 的真实来源 E2E

- 从 UI 创建真实关注任务，不直接改 SQLite。
- 等待真实 planner 与 Runner 发起至少一次 live 检测，不调用隐藏测试接口。
- 在 UI 核对检测时间、规范化摘要和最后成功时间，并与官方页面人工比对。
- 通过同一生产通知代码路径向真实账号发送“验收测试”，确认实际到达和链接可打开。
- 捕获自然变化时，归档内容哈希、SQLite 快照、事件、Job、投递记录、脱敏渠道 ID 和收件截图的关联证据，构成 E3。

Playwright 不登录医院账号，不自动点击预约提交。网络记录必须证明应用没有调用验证码、实名、医保、确认或付款接口。

## 9. 全新 clone 本地 smoke 与 GitHub CI

### 9.1 全新 clone smoke

RC 在隔离临时目录或干净本机账号执行，不复用原工作区依赖、构建产物、数据目录、环境变量、后台进程或 Browser profile：

1. clone 发布候选 tag/commit，确认工作树干净。
2. 验收机除 Git 外只预装 `.nvmrc` 指定的 Node.js 与自带 npm；不得预装项目专用数据库、缓存、队列或任务服务。
3. 仅执行公开文档中的 `npm ci`；锁文件必须保持不变。真实 Playwright 所需浏览器由仓库提供的 npm 安装流程准备，不要求用户维护常驻浏览器服务。
4. 从示例配置创建本机配置。缺少必填项时给出可操作错误；真实通知密钥只由本机环境注入。
5. 使用新的空数据目录执行正式 migration；重复迁移幂等。若验证升级，先复制上一版本脱敏数据库并确认升级前自动备份。
6. 仅执行 `npm start` 启动单个 Node.js 主进程；HTTP、planner、Runner 和 notifier 均随之就绪，不要求另开终端启动组件。
7. 通过 UI/API 完成 E1 闭环，发送 `SIGTERM`，确认优雅退出；再次 `npm start` 后任务、历史、未来调度和去重状态恢复。
8. 执行批准的 live probe 和真实通知送达，测试备份创建、完整性验证与恢复。
9. 收集 Node/npm 版本、安装/迁移输出、进程树、健康接口、脱敏日志和测试报告，随后删除临时数据与密钥。
10. 在第二个全新目录重复最小 smoke，证明不依赖首次运行遗留状态或机器专属绝对路径。

通过标准：无需修改源码、无需猜命令、无需安装或启动外部服务；`npm ci` 后 `npm start` 单进程就绪；真实 SQLite、Runner 和 Playwright 闭环成功；重启与备份恢复通过；隐私扫描零命中。

### 9.2 GitHub CI

稳定开源版的 required checks：

1. 干净 checkout 后以 `npm ci` 安装，校验 lockfile 未变化。
2. 使用 `.nvmrc` 的 Node.js，并通过 `npm ci` 安装锁定版本的 `better-sqlite3`；不安装数据库或队列服务。
3. 对每个声明支持的平台运行 lint、类型检查、单元/契约、磁盘 SQLite 集成、进程 Runner 集成、Playwright E2E 和 build；首版至少覆盖 PRD 确认的平台。
4. 从空数据目录迁移，验证 migration checksum、进程单实例、`SIGTERM` 清理和无残留数据库句柄/profile。
5. 失败 artifacts 先做隐私扫描；不上传 SQLite/WAL/SHM、备份、完整 Trace、Browser profile 或真实消息正文。
6. fork PR 使用只读最小权限和非敏感 fixture，不注入 live 会话或通知密钥；第三方 Action 固定版本。
7. 增加仓库架构扫描，阻止新增外部数据库、缓存、队列服务配置或要求独立后台执行进程的安装文档。

GitHub CI 只证明开源安装与确定性流程可复现，不能替代本机 live、真实通知或 E3。

## 10. 故障注入与恢复

| 注入点 | 故障 | 必须观察到的行为 |
| --- | --- | --- |
| SQLite 锁 | 第二连接持有写锁，触发 busy | 有界等待/重试；HTTP 返回可操作错误；Runner 稍后重试；无半写、无事件重复 |
| SQLite 主文件 | 截断/翻转测试副本，`integrity_check` 失败 | 启动失败并停止监测；不继续写坏库；提示从已验证备份恢复 |
| SQLite 备份 | 最新备份损坏或复制中断 | 原子备份不覆盖旧备份；完整性检查拒绝坏备份；可回退到最近有效备份 |
| migration | SQL 中途失败或 checksum 不符 | 事务回滚；应用不 ready；升级前数据库与备份仍可恢复 |
| 主进程 | 到期 Job 各阶段发送 `SIGTERM` 后重启 | 优雅停止领取；持久 Job 恢复；无已提交事件丢失或重复通知 |
| 单实例 | 同一数据目录二次启动 | 第二实例在任何来源请求前失败，不并发执行 Job |
| 本机休眠/停机 | 模拟长时间时钟跳跃 | 记录监测空窗；恢复先建基线；不补造空窗事件 |
| 官方网络 | DNS、连接超时、重置、慢响应 | 有界超时与持久退避；`unknown/degraded`；不误报无号 |
| 官方响应 | 403、429、5xx、空页、登录墙、验证码、字段缺失 | 分类正确；尊重 `Retry-After`；不绕过、不升频；保留最后可信状态 |
| Playwright | 页面/Browser 崩溃、重定向循环、DOM 漂移 | Context 回收；结构化失败；Runner 可控重试；健康状态可见 |
| 通知 | 429、5xx、连接超时 | 1/5/15 分钟持久重试，最多 3 次；最终失败可见 |
| 通知不确定 | 发送过程中断，无法确认是否接受 | 标记 `delivery_unknown`；重启不自动重复发送；允许用户明确处理 |

演练必须同时验证可观测性和恢复：相关 ID、最近成功/失败、Job 状态、下次动作、Adapter 健康均可查。不能以“删掉数据库重新开始后正常”代替恢复能力。

## 11. 隐私、日志脱敏与安全边界

### 11.1 隐私金丝雀

将虚构秘密放入请求头、query、来源响应、异常、Job payload、通知和 Browser Context，运行成功与失败全链路后扫描：

- SQLite 主库、WAL/SHM、备份和 migration 失败副本；
- 应用、Runner、Adapter、通知和 Browser 日志；
- Trace、metrics、错误对象、诊断导出；
- Playwright 截图、视频、Trace 与 profile；
- fixture、GitHub Actions 输出和 artifacts；
- 仓库工作树及 Git 历史。

完整 Cookie、Token、账号密码、身份证号和医保卡号必须零明文命中。医生/科室偏好也按敏感偏好处理，不进入遥测或过度日志。脱敏覆盖大小写 header、嵌套 JSON、表单、URL 编码、异常 cause 和日志换行；失败时丢弃字段，不回退打印原文。

验证 30 天快照、90 天事件/投递记录及备份保留策略实际执行。SQLite 与备份位于仓库外并使用当前用户权限；诊断导出移除用户目录绝对路径。

### 11.2 安全边界

- **本机访问**：HTTP 固定绑定 `127.0.0.1`；非 loopback 配置拒绝启动。覆盖 Host/DNS rebinding、Origin、CSRF、CORS 和本机恶意网页请求。
- **SSRF/出网**：Adapter 只访问 manifest allowlist；每次重定向重新校验域名与解析 IP，阻止 loopback、私网、链路本地、云元数据和非 Web scheme。
- **注入/XSS**：来源内容、医生名、错误文本全部不可信；覆盖存储型 XSS、SQL 参数化、URL 注入和日志注入。
- **单实例与本地文件**：同一数据目录只能有一个主进程；数据库、备份、日志、profile 和 secret 不进入仓库或公开 issue。
- **凭据**：通知密钥仅由本机环境注入，不进入前端 bundle、SQLite、备份、日志、健康接口或发布包。
- **能力边界**：网络审计证明没有预约提交、验证码识别、实名、医保和付款调用；官方跳转后不自动操作。
- **访问克制**：最小 5 分钟间隔、单来源并发 1、退避和抖动不可由普通配置绕过；不使用代理或账号轮换。
- **供应链**：锁定 Node/npm 依赖，扫描高危漏洞、安装脚本和发布包；GitHub workflow 最小权限且固定第三方 Action。

## 12. live 验收与观察期

发布前固定并记录：

- 同仁医院崇文门院区鼻科；
- 协和医院或北大第一医院皮肤科的最终目标；
- 每个来源的 A/B/C 等级、官方域名、Adapter 版本、最短间隔与已知限制；
- 首个真实通知渠道和测试收件账号；
- 支持的本机操作系统、CPU 架构及 Node.js 版本。

观察流程：

1. 从通过第 9.1 节的全新 clone 环境创建两个真实关注任务。
2. 连续运行至少覆盖一次已知常规放号时刻；RC 最少 24 小时，稳定版按 PRD 执行 7 天 soak。
3. 随机抽查 live 结果并与同一时刻官方页面比对，记录成功率、429、失败分类和最后成功时间。
4. 验证放号前 5 分钟提醒在真实时钟下送达。
5. 出现自然变化时核对通知摘要和官方状态，并记录抓取完成至渠道接受的延迟。
6. 点击官方入口确认医院/院区/科室正确，随后停止，不提交预约。
7. 对 SQLite、备份、日志、浏览器和 artifacts 执行隐私扫描。

若至少一个首批目标没有稳定合规的 A 级 live 来源，只能验收规则与定时提醒，不能声称状态监控或退号监控真实可用。

## 14. 发布门禁与验收包

### 14.1 门禁

- 每次提交：静态、领域、契约、migration checksum 和 fixture 回放。
- 每次 PR：GitHub CI 的真实磁盘 SQLite、HTTP、生产 Runner、真实 Playwright、隐私扫描和架构扫描。
- 每个 RC：全新 clone smoke、SQLite busy/损坏与备份恢复、`SIGTERM`/重启、网络/来源失败、通知重试、live canary、真实送达和安全测试。
- 最终发布：全部 P0 通过；E3 缺失时必须显式标为条件验收，不能宣传现场闭环已证实。

不允许靠重跑隐藏 flaky 测试。live 因官方维护失败可以改期，但不能改用 mock 标绿。

### 14.2 验收包

归档以下脱敏材料：

- commit、release tag、lockfile hash、Node/npm/OS 版本和 Adapter 版本；
- GitHub Actions URL、自动化、Playwright、全新 clone smoke、故障和安全报告；
- migration/`integrity_check`/备份恢复记录；
- fixture 来源元数据与 hash；
- live 人工比对、请求频率和健康时间线；
- 真实通知截图、脱敏渠道 ID；
- 快照、事件、Job 和投递的关联 ID；
- 已知限制、条件通过项、责任人和复验条件。

验收负责人必须能回答：数据来自哪里、何时检测、如何判定变化、事实如何持久化、进程重启后如何恢复、消息是否真的送达、失败是否会误报、是否越过预约与隐私边界。任何一项只能用 mock 截图回答，都不算“真实可用”。
