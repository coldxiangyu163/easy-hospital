# 北京挂号雷达——稳定范围 PRD

| 项目 | 内容 |
|---|---|
| 文档版本 | v0.1-stable |
| 文档状态 | 已冻结；PD-01～PD-05 已决策 |
| 稳定版本线 | 自 `v0.1.0` 起 |
| 产品形态 | 单用户、稳定开源、仅本地运行的 Web 工具 |
| 默认时区 | `Asia/Shanghai` |
| 启动契约 | 完成安装和配置后，在仓库根目录执行 `npm start` |

## 1. 产品结论

北京挂号雷达帮助用户查看北京目标医院的官方放号规则，在本机低频检查受支持的官方公开排班，并通过本机配置的渠道提醒用户。用户收到提醒后必须前往官方渠道，自行完成登录、验证码、实名、医保、确认和付款。

稳定产品不是自动抢号器，也不是实时号源库存系统。当前稳定承诺只有：

1. 北京协和医院东单院区皮肤科公开页面的**新排班发布**（`schedule_released`）；
2. 北京同仁医院崇文门院区鼻科的 **C 级规则提醒**。

`availability_changed_to_available`、`cancellation_slot_detected` 和 Browser Agent 都属于实验/P1。它们可以在明确配置和测试场景中出现，但不能写入稳定版本的实时号源、退号现场闭环或预约成功承诺。

## 2. 用户与价值

| 用户 | 稳定需求 |
|---|---|
| 就诊人或家属 | 少记规则、少反复查看公开排班，在值得打开官方渠道时收到提醒 |
| 本地实例维护者 | 用 Node.js、npm 和一条启动命令运行；数据留在本机；故障与能力边界可见 |

产品衡量“公开排班/规则提醒是否可信”，不衡量最终挂号成功率。医院页面、号源竞争、通知服务和用户设备均可能变化。

## 3. 稳定能力边界

| 目标 | 稳定能力 | 明确不承诺 |
|---|---|---|
| 北京协和医院东单院区皮肤科 | 以 A 级、无需登录的官方公开排班页低频检查；基线后首次出现匹配排班时产生 `schedule_released` | 实时余号、剩余数量、从无号变有号、退号、排班移除或停诊 |
| 北京同仁医院崇文门院区鼻科 | 保存需人工复核的规则，在预计放号时刻前提醒，并提供官方入口 | 读取小程序私有号源、医生/职称/时段匹配、实时有号或退号监测 |

排班不等于号源。`schedule_released` 只表示官方公开页面出现新的排班，不表示该排班仍可预约。

### 3.1 实验/P1 能力

- `availability_changed_to_available`：只有连续的、明确的 `unavailable → available` observation 才可生成；当前不属于真实医院稳定声明。
- `cancellation_slot_detected`：对近期 `unavailable → available` 的保守推断，文案必须写“疑似退号回流”；当前不属于真实医院稳定声明。
- Browser Agent：默认关闭，只在用户本机、显式配对后接收脱敏 observation；真实会话、selector 和长期稳定性尚未形成稳定承诺。
- 实验能力失败必须返回 `unknown` 或显示不可用，不能降级成“无号”。

## 4. 核心产品规则

### 4.1 来源等级

| 等级 | 定义 | 当前行为 |
|---|---|---|
| A | 无需登录的官方公开来源 | 协和公开排班；仅声明 manifest 明确支持的事件 |
| B | 本机 Browser Agent 借助用户已有浏览器页面提交脱敏状态 | 实验/P1，默认关闭 |
| C | 无合规公开状态来源，只能依据已核验规则 | 同仁鼻科只提供规则提醒，不运行号源检查 |

### 4.2 关注任务

- 日期必须落在北京时间今天至今天加 14 天（含两端），且结束日期不早于开始日期。
- 协和任务可以按当前界面支持的医生、日期和时段条件匹配公开排班；不能把职称筛选写成已稳定支持。
- 同仁 C 级任务由客户端规范化为：`matchMode=any_expert`、`doctorName=null`、空职称、`session=ANY`、只订阅 `schedule_released`，并设置规则提醒分钟。
- API 不静默改写不合规的 C 级 payload，而是返回 `SOURCE_POLICY_VIOLATION`。
- 创建后任务默认启用；编辑、停用、恢复和删除必须保留可解释的持久状态。

### 4.3 监测、基线与空窗

- 当前协和来源有效最小检查间隔为 2 小时；同 scope 的多个任务复用来源检查。
- 首次成功检查只建立 baseline，不产生 `schedule_released`。
- `unknown`、登录墙、验证码、限流、异常空页或解析失败不能被写成“无号”。
- 进程停止、电脑休眠或网络中断期间不继续监测。
- 恢复时，只有距上次来源尝试超过有效最小间隔的 2 倍才删除旧 baseline 并静默重建；协和当前 grace 为 4 小时。空窗差异不冒充新事件。

### 4.4 规则提醒与通知

- 规则提醒以不可变的计划提醒时刻建立批次，以对应放号时刻 `occurrenceAt` 作为最晚发送/重试截止时间。
- 可重试失败在截止前使用 1、5、15 分钟阶梯；重试时间不越过 `occurrenceAt`。
- 截止后，从未尝试的提醒记录 `RELEASE_REMINDER_MISSED`；已有渠道尝试的提醒记录 `RELEASE_REMINDER_RETRY_EXPIRED`，不继续补发。
- 每个渠道只有成功原子 claim 到 `sending` 后才能执行发送并回写结果，避免规则变更与投递并发覆盖批次终态。
- 规则新增、编辑、停用或删除后按医院/院区/科室 scope 立即 reconciliation；唯一首选规则接管未来提醒，旧批次进入 `RULE_CHANGED` 或 `RULE_DELETED`，已发送记录不被抹除。
- macOS 本机通知、Bark、SMTP 只在各自运行条件满足时启用；“渠道接受”不等于用户一定收到，使用者必须自行测试。

### 4.5 官方入口与域政策

- migration 17 的 `hospital_domain` 是规则 URL 域政策的数据库事实源。
- `officialEntryUrl` 必须命中该医院登记为 `official` 的域。
- `sourceUrl` 必须命中该医院登记为 `evidence` 的域；同一官方域如也可作为证据，应分别登记对应 kind。
- 未登记医院/域、非 HTTPS URL 或 catalog scope 不一致时拒绝写入。

## 5. 稳定用户故事与验收

### US-S-01 查看规则与来源

- 规则页显示医院、院区、科室、放号时间、对应就诊日期、官方入口、来源、核验时间、可信度和需复核状态。
- 规则不是医院承诺；超过复核期时必须显示提示。
- 官方入口只打开允许的 HTTPS 官方域。

### US-S-02 创建和管理任务

- 创建、编辑、启停和删除通过真实本地 API 与 SQLite 持久化。
- 非法日期、catalog 引用和 C 级来源政策在写入前被拒绝。
- 重启后任务及未来调度恢复；任务版本阻止陈旧写入覆盖新状态。

### US-S-03 接收同仁 C 级规则提醒

- 在计划提醒时刻生成一次规则提醒；文案描述“预计放号/规则提醒”，不声称新排班或有号。
- 规则变更后旧时刻不发送，当前首选规则即时接管。
- 失败重试不越过放号时刻；过期原因在通知列表可见。

### US-S-04 接收协和新排班提醒

- baseline 后首次出现满足任务条件的新排班时产生一次 `schedule_released`。
- 重复快照、来源异常和长空窗后的首次恢复检查不产生假事件。
- 通知明确“排班不代表可预约状态”，并提供官方入口。

### US-S-05 故障、恢复与隐私

- SQLite 完整性、migration manifest 或历史 checksum 异常时 fail closed。
- migration 前创建一致性备份；恢复必须停机，并与应用启动共用同一数据库实例锁。
- 数据目录、数据库、WAL/SHM、备份和生产 `.env` 在支持的平台收紧为当前用户权限。
- 不保存医院账号、Cookie、Token、身份证、医保卡、病历或支付信息；默认无遥测和项目自有后端。

## 6. 非目标

- 自动抢号、预约、取号、验证码处理、实名、医保、确认或付款。
- 逆向微信/支付宝/抖音小程序私有接口。
- 高频轮询、代理池、IP 轮换、多账号或风控规避。
- 多用户 SaaS、远程控制面、云同步、公网部署或遥测。
- Docker、PostgreSQL、Redis、外部队列或必须单独维护的服务。
- 对实时余号、退号、通知送达、规则永久准确或预约成功作保证。

## 7. 冻结决策 PD-01～PD-05

| ID | 决策 | 稳定约束 |
|---|---|---|
| PD-01 | 首批皮肤科目标为北京协和医院东单院区皮肤科 | 只承诺公开排班 `schedule_released`；不扩大为实时号源 |
| PD-02 | 无稳定 A 级实时号源时接受 C 级降级；B 级不进入稳定 P0 | 同仁为规则提醒；Browser Agent 与实时状态事件保留实验/P1 |
| PD-03 | 首个外部通知选择 Bark；运行时同时支持条件启用的 macOS 本机通知与 SMTP | 每个实际启用渠道均需用户自检；多渠道是并发投递，不是主备 |
| PD-04 | MIT License | 仓库保持 `private: true`，不发布 npm 包；源码按 MIT 分发 |
| PD-05 | 正式支持 macOS 14+ | Ubuntu CI 用于兼容性验证；Windows 不属于当前正式支持承诺 |

这些决策已经冻结。调整目标医院、把 B 级/实时状态升为稳定能力、改变许可证或扩大正式平台，都必须另开产品变更，不在补丁版本中静默发生。

## 8. 稳定发布门禁

稳定补丁版本至少要求：

1. `npm ci --ignore-scripts` 可从锁文件重复安装，依赖版本和 `package.json` 一致；
2. lint、类型检查、自动化测试、构建、Playwright E2E、release metadata 和 production smoke 通过；
3. 真实磁盘 SQLite migration、checksum、单实例、备份和恢复测试通过；
4. 涉及 schema 17 的候选完成 v16 → v17 备份、迁移、重启和恢复演练；
5. 协和 `schedule_released` 与同仁 C 级规则提醒的 fixture/集成/用户流程门禁通过；
6. 来源测试与 E2E 禁止真实医院外联和真实通知，live/真实渠道只能由维护者显式执行；
7. 仓库、日志、SQLite、Fixture 和 artifacts 的隐私检查无真实密钥、会话或机器专属信息；
8. CHANGELOG、README、配置、测试策略、版本号和锁文件与候选一致。

自然发生的实时余号/退号 E3 和 7 天 soak 是将对应实验能力升级为稳定声明的门槛，不阻塞只修复协和排班、同仁规则提醒、存储、安全或 UI 的补丁版本。

## 9. 发布与回滚

- 稳定版本从 `v0.1.0` 开始使用语义化标签，不要求等待某个主版本号才称为稳定。
- 发布前停止应用并保留升级前备份；migration 失败时不启动新版本。
- 回退代码时恢复与旧版本 schema 匹配的备份，不执行破坏性降级 migration。
- 回滚后不补造停机期间事件；按第 4.3 节的 grace/baseline 规则恢复。
- 发现敏感数据落库、来源越界、通知风暴或自动预约行为时立即停机，修复和验证后再恢复。
