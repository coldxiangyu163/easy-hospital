## 1. 产品结论

“北京挂号雷达”帮助一个真实用户维护北京目标医院的官方放号规则，低频监测公开号源变化，在放号前或检测到可预约号源时提醒用户，并把用户送到官方渠道完成人工预约。

首版应做成**单用户、稳定开源、仅本地运行版**，代码发布到 GitHub `easy-hospital`，而不是自动抢号器、多用户 SaaS 或需要远程服务端的混合产品。产品价值不是“保证挂上号”，而是减少用户反复刷新、错过固定放号时间和退号回流的概率。

新增用户决策优先于来源摘要中的交付技术约束：首版**明确不使用 Docker、PostgreSQL 或 Redis**。应用采用单个本地 Node.js 进程承载 Web/API、调度、来源检查和通知，使用 SQLite 做持久化；用户完成一次依赖安装和本地配置后，只需在仓库根目录执行 `npm start`。

本方案最脆弱的前提是：**至少一个首批目标存在可稳定、合规读取的 A 级公开号源来源，且用户运行期间本机保持唤醒和联网**。如果前一条件不成立，P0 只能提供规则日历与定时提醒，不能声称“实时号源监控”或“退号监控”；如果后一条件不成立，产品必须明确显示监测空窗，不能暗示离线期间仍在监测。

## 2. 目标与成功指标

### 2.1 MVP 目标

1. 覆盖北京同仁医院崇文门院区鼻科，以及北京协和医院/北京大学第一医院皮肤科二选一的真实官方规则。
2. 用户可在 3 分钟内建立一个未来 14 天内的关注任务。
3. 至少一个首批目标可从真实来源完成“查询—归一化—变化识别—真实渠道通知—跳转官方入口”的闭环。
4. 来源失效或本地进程停止时明确显示“未知/监测已停止/来源异常”，不把查询失败或离线空窗误报为“无号”。
5. 全流程不保存医院账号、Cookie、Token、身份证、医保卡或医疗档案。
6. 开源用户在受支持系统上完成 `npm ci` 和本地配置后，可用一条 `npm start` 启动全部运行组件，无需 Docker、数据库服务或队列服务。

### 2.2 成功指标

上线后首个 14 天观察周期内：

- 两个首批目标的规则字段完整率为 100%，每条规则均有可访问的官方来源和最后核验时间。
- 用户至少创建并持续启用 1 个真实关注任务 7 天。
- 在来源可用时，定时检查成功率不低于 95%；维护窗口和用户设备断网时段单独记录，不计入分母。
- 从一次成功检查识别出事件到通知渠道接受发送请求，P95 不超过 60 秒。
- 放号前 5 分钟提醒的发送时间误差不超过 ±30 秒。
- 同一事件重试导致的重复通知数为 0。
- 抽查至少 30 次真实检查结果，其中随机选择至少 10 次与同一时刻官方页面人工比对，归一化状态一致率为 100%。
- SQLite 数据库、日志、导出物中敏感身份信息与医院会话凭据检出数为 0。
- GitHub `easy-hospital` 的发布提交在全部受支持系统上通过 CI，且仓库不包含密钥、构建产物、个人数据或机器专属绝对路径。

这些指标衡量“监测和提醒是否可信”，不以最终挂号成功率作为产品成功指标，因为验证码、实名、医保、确认、付款和号源竞争均发生在官方渠道且不受本产品控制。

## 3. 用户与使用场景

### 3.1 用户角色

| 用户 | 特征 | 核心诉求 |
|---|---|---|
| 就诊人/家属（主用户） | 只有一个私有账户；可能同时关注本人和家属需求，但系统不记录身份信息 | 少刷页面、不错过时间、发现回流号后快速进入官方入口 |
| 本地实例维护者（同一人） | 能安装 Node.js、在终端执行 `npm ci`/`npm start`、配置通知凭据、查看来源健康状态 | 安装可重复、一条命令启动、故障可见、无需维护远程服务 |

### 3.2 核心场景

1. **常规放号前准备**：用户查看同仁鼻科规则，建立任务；系统在下一次常规放号前 5 分钟提醒，用户提前打开官方入口并自行登录。
2. **售罄后的可用变化**：用户关注未来 7～14 天的皮肤科专家号；系统在上一次明确“无号”、本次明确“有号”时通知。
3. **退号回流**：某一已发布排班此前明确售罄，之后重新可预约；系统标记为“疑似退号回流”，避免把首次放号误称为退号。
4. **灵活匹配**：用户可指定医生、指定职称，或选择任意可用专家号，并限制日期、上午/下午和院区。
5. **来源异常**：医院页面改版或网络失败时，用户看到失败原因、最后成功时间和数据已过期提示，而不是错误的“无号”。
6. **收到提醒后人工预约**：通知包含检测时间、号源摘要和官方入口；用户自行完成验证码、实名、医保、确认和付款。

## 4. 关键定义与业务规则

### 4.1 来源等级

| 等级 | 定义 | P0 行为 |
|---|---|---|
| A 级 | 无需登录的医院官方公开页面或公开接口 | 可做规则展示、状态监测和变化提醒；默认 P0 数据来源 |
| B 级 | 本地 Agent 借助用户本机浏览器已有会话读取状态，只向同机主进程传递脱敏的“有号/无号/未知”结果 | 默认 P1；若 PD-02 决定提升到 P0，医院 Cookie、Token 仍只能留在浏览器进程，不写入 SQLite 或日志 |
| C 级 | 仅微信小程序或其他不可合规读取的私有入口可查 | P0 仅展示已核验规则并发送定时提醒，不逆向接口、不宣称状态监测 |

### 4.2 标准状态

每次成功检查只能归一化为以下状态之一：

- `available`：官方来源明确表示可预约，或明确剩余数量大于 0。
- `unavailable`：官方来源明确表示无号、约满或剩余数量为 0。
- `unknown`：页面异常、字段缺失、登录墙、验证码、限流、解析失败或无法判断。

`unknown` 不是 `unavailable`，不得触发“从无号变有号”或“退号”判断，也不得覆盖界面上的最后一次明确状态；界面必须同时标注该明确状态的检测时间和当前来源异常。

### 4.3 号源唯一键

在单个来源内，以“医院 + 院区 + 科室 + 就诊日期 + 上午/下午 + 医生或来源排班标识”构成号源唯一键。来源没有稳定排班标识时，适配器使用上述可见字段生成稳定哈希，但不得把患者信息放入哈希输入。

### 4.4 三类事件

| 事件 | 可执行判定 |
|---|---|
| `schedule_released` | 某就诊日期/排班在上一次成功快照中不存在、本次成功快照中首次出现；首次接入来源建立的基线快照不产生事件 |
| `availability_changed_to_available` | 同一号源唯一键的上一个明确状态为 `unavailable`，本次成功状态为 `available` |
| `cancellation_slot_detected` | 已发布排班的同一号源唯一键在最近 30 分钟内曾明确为 `unavailable`，本次变为 `available`；这是对回流号的保守推断，用户文案必须写“疑似退号回流” |

一次状态变化可以同时满足后两类事件。若同一任务同时订阅两类事件，只发送一条聚合通知并列出两个事件标签。

### 4.5 查询频率与时间

- P0 默认在每日 06:00～23:00（`Asia/Shanghai`）监测，每个上游来源最短 5 分钟检查一次。
- 多个任务命中同一来源和查询条件时必须复用一次检查结果，不得按任务重复请求上游。
- 单个来源同一时刻最多 1 个请求；失败后按 5、15、30、60 分钟退避，成功后恢复 5 分钟周期。
- 常规放号提醒由本地规则调度产生，不需要在放号时刻高频刷新。
- 如官方规则或服务条款要求更低频率，以官方限制为准，并在来源详情页显示实际检查周期。

### 4.6 去重与冷却

- 事件指纹由“任务 + 事件类型 + 号源唯一键 + 前后快照标识”组成；同一指纹只通知一次，任务重试或进程重启不得重复发送。
- 每个任务发送一条通知后进入 60 秒冷却；冷却期间出现的不同新事件不丢弃，在冷却结束时聚合发送。
- 同一号源再次从 `available` 回到 `unavailable`，之后又变为 `available`，属于新的状态序列，可以再次提醒。
- 放号前提醒按“规则 + 本次放号时刻 + 任务”去重，每个时刻只发送一次。

### 4.7 规则可信度与过期

- 规则必须包含：医院、院区、科室、提前预约天数、常规放号时间、当日剩余号规则、官方入口、信息来源、最后核验时间、可信度、是否需要重新确认。
- 信息直接来自当前可访问的官方页面且 30 天内人工核验，可信度为“高”。
- 最后核验超过 30 天自动标记“需要重新确认”；超过 90 天同时把可信度降为“低”。
- 低可信度规则仍可展示和提醒，但通知必须带“规则可能已变化，请以官方页面为准”。

## 5. 范围与非目标

### 5.1 P0 范围（上线必需）

1. 两个首批目标的放号规则日历与规则新增、编辑、停用。
2. 关注任务的创建、查看、编辑、启停和删除。
3. 指定医生、职称条件、任意专家三种匹配方式。
4. 未来 14 天内的日期、上午/下午、院区和三类事件筛选。
5. 放号前 5 分钟提醒、状态变化提醒、疑似退号回流提醒。
6. 一个真实通知渠道、通知去重、冷却、失败重试和发送结果可见。
7. `SourceAdapter` 隔离、A 级来源读取、C 级来源诚实降级、脱敏快照与来源健康状态。
8. 本地 Web 管理端、SQLite、进程内 Scheduler/Job Runner、按需使用的 Playwright Browser；`npm start` 一条命令启动全部运行组件。
9. GitHub `easy-hospital` 稳定开源交付：版本化发布、锁文件、安装/运行/排障文档、许可证、安全说明和受支持平台 CI。
10. 自动化测试、健康检查、可重复演示数据流和真实来源验收流程。
11. 隐私边界、默认无遥测、低频访问、官方跳转和明确免责声明。

### 5.2 P1 范围（不阻塞个人 MVP 上线）

1. B 级本地浏览器 Agent 与脱敏结果上报。
2. 第二通知渠道及渠道故障自动切换。
3. 规则变更历史、双来源交叉核验和核验提醒工作流。
4. 用户自定义安静时段与摘要通知。
5. 更长时间的趋势报表和来源成功率图表。

PD-02 若把 B 级来源提升到 P0，则 P1-01 自动成为上线门槛，其余 P1 仍不阻塞。

### 5.3 明确非目标

- 自动提交预约、自动确认或自动付款。
- 验证码识别、验证码绕过或任何风控规避。
- 多账号并发、批量账号、号源占位、代理池、IP 轮换或高频轮询。
- 多用户 SaaS、公开注册、团队权限、付费订阅。
- 上传或保存医院 Cookie、Token、账号密码。
- 保存身份证、医保卡、手机号、病历、诊断或完整医疗档案。
- 逆向微信小程序私有接口、解密私有协议或模拟签名。
- 对挂号结果、号源真实性或就医效果作保证。
- 首版覆盖北京全部医院、全部院区或全部科室。
- 在产品内完成官方渠道的实名、医保和支付流程。
- Docker、Docker Compose、PostgreSQL、Redis 或任何必须常驻的外部基础设施服务。
- 远程控制面、云端同步、遥测上报、用户注册或必须联网的产品账号。
- P0 自动更新器、托盘常驻程序和系统开机自启；首版由用户在终端显式运行 `npm start`。

## 6. 端到端流程与系统约束

```text
用户浏览器 ──> 本地 Web/API ───────────────> SQLite
                     │                         ▲
                     ├──> 进程内 Scheduler     │
                     │         │               │
                     │         v               │
                     │      Durable Job Runner ├──> SourceAdapter ──> 官方来源
                     │         │               │
                     │         └──> 事件判定 ──┘
                     │                    │
                     └<── 健康/任务/状态 <─┼──> Notifier ──> 真实通知渠道
                                          │
                                          └──> 脱敏快照与发送记录

仓库根目录：npm start ──> 启动上述全部本地组件
```

约束：

- `npm start` 必须启动单个本地 Node.js 主进程；Web/API、Scheduler、Job Runner、Notifier 均在该进程内运行，不要求用户另开 PostgreSQL、Redis、Worker 或 Docker。
- SQLite 是 P0 唯一持久化存储；持久任务、事件发件箱和唯一约束必须保证崩溃恢复与去重，不能只依赖内存定时器。
- 同一数据目录只允许一个主进程持有运行锁；第二次启动必须安全失败并指出已有实例，而不是并发执行来源检查。
- 医院差异必须封装在 `SourceAdapter`，调度、事件判定和通知层不得依赖医院页面字段。
- Playwright 只用于读取无需登录的官方公开页面或执行自动化测试；P0 不注入用户医院会话。
- 快照只保存归一化业务字段、检测时间、来源标识、内容哈希和脱敏失败原因，不保存完整页面、请求头或响应中的身份字段。
- 可用性快照保留 30 天，事件和通知记录保留 90 天，到期自动删除。
- 通知渠道密钥只通过本地运行环境注入，不显示在 Web 页面、不写入 SQLite、不进入日志。
- 应用默认不发送遥测。除医院官方来源、用户选定的通知渠道和用户主动访问的 GitHub 链接外，不得连接项目自有远程服务。

## 7. P0 用户故事与逐条验收标准

> 规则：所有 P0 验收均必须通过；涉及来源变化的自动化测试使用固定夹具重放，另由第 10 节真实来源门槛防止“只对假数据可用”。

### US-P0-01 查看真实放号规则

**故事**：作为就诊人，我希望查看目标医院的放号规则和来源，以判断何时准备挂号。

**验收标准**：

1. 给定两个首批目标均已录入规则，打开规则页时，逐条显示第 4.7 节规定的全部 11 个字段；任一字段为空则该规则不能标记为“可用”。
2. 给定规则的官方入口和信息来源 URL，点击后在新窗口打开配置的 HTTPS 官方域名，不经过非官方短链。
3. 给定一条最后核验时间为当前日期 31 天前的规则，刷新页面后显示“需要重新确认”；给定 91 天前的规则，同时显示“低可信度”。
4. 给定一条“提前 7 天、每日 07:00 放号”的规则，日历必须同时显示本次放号时刻及对应就诊日期，时区为 `Asia/Shanghai`。
5. 按医院、院区、科室筛选时，结果只包含同时满足全部所选条件的规则；清空筛选后恢复全部规则。

### US-P0-02 维护放号规则

**故事**：作为私有实例维护者，我希望在官方规则变化后更新记录，使提醒有可追溯依据。

**验收标准**：

1. 新增规则时，缺少医院、院区、科室、放号时间、官方入口、信息来源或最后核验时间中的任一项，保存操作被阻止并定位到具体字段。
2. 官方入口或信息来源不是 HTTPS，或域名不在该医院配置的官方域名列表中时，保存操作被阻止并显示原因。
3. 编辑提前预约天数或常规放号时间后，尚未发送的未来提醒在 1 分钟内按新规则重新计算；旧时刻不再发送。
4. 停用规则后，不再生成新的放号前提醒，但历史事件与通知记录保留到既定保留期限。
5. 每次新增或编辑规则均记录操作时间和变更后内容；SQLite 记录中不得出现通知密钥或医院登录信息。

### US-P0-03 创建关注任务

**故事**：作为就诊人，我希望按自己的就诊条件建立任务，只接收相关提醒。

**验收标准**：

1. 创建任务必须选择医院、科室、日期起止、时段和至少一个事件类型；缺失任一必填项时不能保存。
2. 日期只能落在当前自然日至当前日期加 14 天之间，结束日期不得早于开始日期；非法日期保存失败并显示允许范围。
3. 医生条件必须且只能选择“指定医生”“指定职称”“任意专家”之一；选择前两者时必须填写对应医生或职称。
4. 院区可选择一个指定院区或“不限院区”；选择指定院区后，其他院区的号源不得命中任务。
5. 时段可选择“上午”“下午”或“不限”；选择“上午”后，下午号源不得命中任务。
6. 保存成功后任务默认启用，1 分钟内进入调度，并显示下一次检查时间、当前状态和最近一次成功检查时间；首次基线检查不发送变化通知。

### US-P0-04 管理关注任务

**故事**：作为就诊人，我希望编辑、暂停、恢复和删除任务，避免无效提醒。

**验收标准**：

1. 编辑任务筛选条件并保存后，下一次检查只按新条件匹配，旧条件不再产生通知。
2. 暂停任务后 1 分钟内停止新检查和通知；暂停期间已排队但未发送的通知被取消并记录“任务已暂停”。
3. 恢复任务后 1 分钟内重新进入调度，先建立当前基线，不把暂停期间的未知变化当作退号事件。
4. 删除任务必须二次确认；确认后任务不再出现在活动列表且不再调度，历史事件保留 90 天并标记原任务已删除。
5. 任务列表展示启用状态、筛选摘要、最近明确号源状态、状态检测时间、来源健康状态和下一次动作。

### US-P0-05 接收放号前 5 分钟提醒

**故事**：作为就诊人，我希望在常规放号前收到提醒，以便提前打开官方渠道。

**验收标准**：

1. 给定规则下一次放号时间为 07:00、任务启用且订阅 `schedule_released`，使用可控时钟推进到 06:55 时，只生成一次提醒。
2. 提醒发送时间相对 06:55 的误差不超过 ±30 秒，并显示目标医院、院区、科室、预计放号时间、对应就诊日期范围和官方入口。
3. 服务在 06:54 重启并于 06:55 前恢复时，仍发送一次提醒；重启前后合计不得多于一次。
4. 服务在计划提醒时间后 5 分钟以上才恢复时，不补发已失去准备价值的提醒，记录“错过提醒”并在界面可见。
5. 规则被标记“需要重新确认”时仍可提醒，但通知必须明确提示规则可能变化并显示最后核验日期。

### US-P0-06 识别新排班发布

**故事**：作为就诊人，我希望在新的排班被官方发布时收到提醒。

**验收标准**：

1. 重放“上一成功快照无目标排班、本次成功快照出现目标排班”的夹具时，生成一个 `schedule_released` 事件。
2. 首次接入来源、系统只有当前快照而没有上一次成功快照时，只建立基线，不生成 `schedule_released`。
3. 新排班不满足任务的院区、日期、时段或医生条件时，不生成该任务的事件。
4. 同一快照因 Job Runner 重试处理 3 次时，事件表只有一条记录且最多发送一条通知。
5. 本次快照为 `unknown` 或解析失败时，不生成新排班事件。

### US-P0-07 识别从无号变为有号

**故事**：作为就诊人，我希望在匹配号源从明确无号变为明确有号时收到提醒。

**验收标准**：

1. 对同一号源唯一键依次重放 `unavailable`、`available` 两个成功快照时，生成一个 `availability_changed_to_available` 事件。
2. 依次重放 `unknown`、`available` 或首次快照即为 `available` 时，不生成“从无号变有号”事件，但界面显示当前明确有号。
3. 依次重放 `available`、`available` 时不产生新事件。
4. 状态变化不满足任务筛选条件时，不产生该任务的事件。
5. 从成功检查完成到通知渠道接受发送请求，在自动化端到端测试中不超过 60 秒。

### US-P0-08 识别疑似退号回流

**故事**：作为就诊人，我希望识别已售罄排班重新有号的情况，同时不被误导为确定发生了退号。

**验收标准**：

1. 给定排班已发布，且同一号源在最近 30 分钟内从 `unavailable` 变为 `available`，生成一个 `cancellation_slot_detected` 事件。
2. 前一明确快照距本次超过 30 分钟、首次发现排班即有号或排班此前不存在时，不生成退号事件。
3. 所有界面和通知统一使用“疑似退号回流”，不得使用“确定退号”或“保证可挂”。
4. 同一任务同时订阅 `availability_changed_to_available` 和 `cancellation_slot_detected` 时，一次变化只发送一条聚合通知，通知中同时列出两个标签。
5. 号源在提醒后回到 `unavailable`，随后再次变为 `available` 时，生成新的状态序列事件，并受 60 秒冷却规则约束而不是被永久去重。

### US-P0-09 通过真实渠道收到可行动通知

**故事**：作为就诊人，我希望提醒信息完整且能直达官方入口，以便立即人工预约。

**验收标准**：

1. 通知至少包含：人类可读事件类型、医院、院区、科室、就诊日期、上午/下午、医生或职称、检测时间、号源摘要、数据来源状态和官方入口；字段无数据时显示“官方未提供”，不得静默省略关键上下文。
2. 在验收环境配置真实渠道凭据后，从 Web 发起测试通知，目标设备在 2 分钟内收到，系统记录渠道返回的成功结果和发送时间。
3. 官方入口必须与对应规则配置一致；点击后到达官方域名，失败时通知仍保留可复制的完整 URL。
4. 对同一事件模拟 3 次发送重试，目标设备只收到一条；对冷却期内两个不同号源事件，冷却结束后收到一条包含两项摘要的聚合通知。
5. 渠道返回可重试错误时按 1、5、15 分钟重试，最多 3 次；仍失败则标记“发送失败”并在 Web 首页显示，不无限重试。
6. 通知文案明确写明“号源可能瞬时变化，请以官方页面为准；本工具不代替人工预约”。

### US-P0-10 查看来源健康与诚实降级

**故事**：作为维护者，我希望知道来源是否可靠，避免把失效解析器当成无号。

**验收标准**：

1. 每个来源详情显示来源等级、实际检查周期、最后尝试时间、最后成功时间、连续失败次数、最近一次脱敏失败原因和当前健康状态。
2. 连续 1～2 次失败时标记“降级”，连续 3 次失败时标记“不可用”；下一次成功后连续失败数清零并恢复“健康”。
3. 来源失败时任务状态显示“来源异常，最后明确状态为 X（时间）”，不得显示当前“无号”。
4. C 级来源只允许创建规则提醒；选择状态变化或退号事件时界面阻止保存，并解释“该来源仅支持规则提醒”。
5. 解析器遇到登录墙、验证码或限流页时返回 `unknown` 和对应脱敏原因，不尝试绕过、不提升请求频率。
6. 健康检查同时覆盖本地 Web/API、SQLite 读写、Scheduler、Job Runner 和已启用 SourceAdapter；任一关键组件异常时总状态不是“健康”。
7. 用户关闭主进程或电脑从休眠恢复后，首页必须显示监测空窗的起止时间；恢复时先建立基线，不推断空窗期间的状态变化。

### US-P0-11 保护隐私并遵守产品边界

**故事**：作为用户，我希望工具不接触敏感身份凭据，也不会替我执行预约。

**验收标准**：

1. Web 页面和 API 不提供医院账号、密码、身份证、医保卡、验证码、Cookie 或 Token 的录入字段。
2. 对 SQLite 数据库、应用日志、Job Runner 日志和导出演示数据执行关键词及模式扫描，医院凭据和敏感身份信息匹配数为 0。
3. 对运行时出站请求做网络抓包，除医院官方来源、选定通知渠道和用户主动打开的 GitHub 链接外，不得出现项目自有服务、遥测或云同步请求。
4. 快照记录只含第 6 节允许的脱敏字段；自动化测试向来源响应注入模拟手机号、身份证号和 Cookie 后，持久化层与日志中均不存在这些值。
5. 所有“去挂号”操作只打开官方入口，不自动填写、点击确认、提交订单或付款。
6. 当官方来源返回验证码、风控或访问拒绝时，系统停止本次读取并退避，不使用代理、更换账号或并发重试。
7. 删除到期快照和事件的每日任务可重复执行；执行后 30 天前快照和 90 天前事件/通知记录数量均为 0。

### US-P0-12 一条本地命令启动、恢复与演示

**故事**：作为本地实例维护者，我希望无需 Docker 或外部服务即可可靠启动、备份和复现实例行为。

**验收标准**：

1. 在受支持操作系统的全新环境中，安装 `.nvmrc` 指定的 Node.js 版本、克隆 GitHub `easy-hospital`、执行一次 `npm ci` 并完成本地配置后，在仓库根目录只执行 `npm start`，60 秒内全部健康检查通过，终端输出本地 Web URL，浏览器可访问。
2. `npm start` 启动的进程树不得包含 Docker、PostgreSQL 或 Redis，也不得要求用户在另一终端启动 Web、Scheduler、Job Runner 或数据库。
3. 空数据目录首次启动后自动创建 SQLite 数据库，并能看到两个首批目标的已核验规则；不会自动生成虚假的生产号源事件。
4. 执行固定演示流程可依次重放“无号—有号—回到无号—再次有号—来源失败”，并得到与第 4.4 节一致的事件、聚合、去重和降级结果。
5. Job Runner 在事件写入 SQLite 后、通知确认前被强制终止；重新执行 `npm start` 后事件不丢失，目标设备合计至多收到一次通知。
6. 同一数据目录已有实例运行时再次执行 `npm start`，第二个实例在 10 秒内安全退出并说明数据目录已被占用，不发起任何来源请求。
7. 用户按 `Ctrl+C` 后进程在 10 秒内停止接受新任务、提交已完成事务并退出；再次启动时只调度未来任务，不补发已过期提醒，并显示停机空窗。
8. 应用停止后复制 SQLite 数据文件及本地配置，在同版本空目录恢复并执行 `npm start`，规则、任务和去重记录完整，未来提醒继续执行，过去提醒不补发。

### US-P0-13 稳定开源发布

**故事**：作为开源用户，我希望从 GitHub `easy-hospital` 获得可审计、可重复安装和有明确支持边界的版本。

**验收标准**：

1. 目标仓库名称为 `easy-hospital` 且公众无需登录即可读取源码、Issue 模板、发布说明和许可证；许可证必须与 PD-04 的选择一致。
2. 仓库根文档明确写出产品边界、受支持系统、Node.js 版本、`npm ci` 安装、`npm start` 启动、配置、备份、升级、排障和卸载步骤；一名未参与开发的验收者可按文档完成首次运行。
3. 锁文件纳入版本控制；在同一发布提交上连续两次执行 `npm ci`、`npm test` 和 `npm run build` 均成功，且不改变受版本控制文件。
4. GitHub CI 在所有受支持操作系统上执行安装、lint、类型检查、自动化测试和构建；全部必需检查通过后才允许创建稳定版本标签。
5. 仓库包含贡献指南、安全问题私下报告渠道和变更记录；首个稳定版本使用语义化版本标签 `v1.0.0`，GitHub Release 关联冻结提交和已知限制。
6. 对仓库完整历史的发布前扫描不得发现真实密钥、医院会话、个人数据、SQLite 运行数据、日志、构建产物或机器专属绝对路径。
7. 仓库不包含 `Dockerfile`、Compose 配置或要求 Docker 的安装文档；全仓搜索 `docker compose`、`Dockerfile`、`PostgreSQL`、`Redis` 时，不得在运行方案中发现这些依赖，历史需求说明除外。

## 8. P1 用户故事与逐条验收标准

### US-P1-01 使用本地浏览器会话读取 B 级状态

**故事**：作为用户，当公开来源不足时，我希望本机 Agent 借助我已登录的浏览器读取状态，但不保存或上传会话凭据。

**验收标准**：

1. Agent 只通过本机受限进程间接口向主进程传递来源、号源唯一键、归一化状态、检测时间和内容哈希；网络抓包中不含 Cookie、Token、账号、手机号或身份证，也不连接项目远程服务。
2. 浏览器未登录、出现验证码或页面结构变化时返回 `unknown`，本地主进程显示原因且不触发状态事件。
3. 停止本机 Agent 后，任务在两个预期周期内显示“数据已过期”，不沿用旧状态冒充实时结果。
4. 本地主进程不能向 Agent 下发任意脚本或读取浏览器存储，只能请求已安装版本支持的来源检查；浏览器会话不得写入 SQLite 或日志。

### US-P1-02 配置第二通知渠道与故障切换

**故事**：作为用户，我希望主渠道故障时仍能收到关键提醒。

**验收标准**：

1. 用户可配置主、备两个渠道，并分别发送真实测试通知。
2. 主渠道完成 3 次既定重试后仍失败，系统向备渠道发送一次，并在记录中关联同一事件。
3. 主渠道成功时不调用备渠道；进程重启也不得造成双渠道重复发送。

### US-P1-03 核验规则变更历史

**故事**：作为维护者，我希望追踪规则何时、依据什么发生变化。

**验收标准**：

1. 每次规则变更显示变更前后差异、核验时间和官方来源 URL。
2. 两个官方来源内容冲突时，规则显示“存在冲突”，不自动选择更有利的放号时间。
3. 到达 30 天复核期限时生成一次维护提醒；完成核验后更新日期并解除提醒。

### US-P1-04 配置安静时段与摘要

**故事**：作为用户，我希望非紧急消息不在夜间打扰，但不漏掉稀缺号源事件。

**验收标准**：

1. 用户可配置安静时段，并分别设置规则提醒是否延后、状态/退号提醒是否立即发送。
2. 被延后的事件在安静时段结束后合并为一条摘要，摘要中的事件数量和详情与事件记录一致。
3. 用户选择“状态事件始终立即发送”后，安静时段内的匹配状态事件仍在 60 秒目标内送达。

### US-P1-05 查看长期来源趋势

**故事**：作为维护者，我希望根据趋势判断来源是否还值得使用。

**验收标准**：

1. 页面按日展示最近 30 天成功检查数、失败数、成功率和 P95 检查耗时，统计值可由原始健康记录复算一致。
2. 可按来源筛选；无数据日期显示“无检查”，不得显示 0% 误导为全部失败。
3. 数据到达保留期限后按第 6 节规则删除，报表不得绕过保留策略保存明细。

## 9. “真实可用”的定义

只有同时满足以下条件，才能称为“个人可用 MVP”；只跑通演示夹具不能称为真实可用：

1. **真实目标**：同仁崇文门鼻科和 PD-01 选定的皮肤科均有 30 天内核验的官方规则、官方入口和正确院区。
2. **真实数据**：至少一个首批目标通过 A 级来源连续运行 7 天；若没有 A 级来源，则必须先完成 PD-02 并让 B 级能力通过全部 P0 门槛。
3. **真实任务**：用户能用自己的目标日期、时段和医生条件建立任务，界面显示真实最近检查状态，不依赖预置假号源。
4. **真实通知**：选定通知渠道在用户真实设备上收到测试通知和至少一次真实规则提醒；夹具事件仅用于验证不可人为制造的号源变化路径。
5. **可行动**：通知中的链接到达对应医院官方预约入口，后续验证码、实名、医保、确认和付款完全由用户操作。
6. **诚实降级**：来源失败、状态过期、本机停机/休眠空窗、C 级来源和低可信度规则均有醒目标识，不以缓存或推断伪装实时结果。
7. **本地可持续运行**：在本机保持唤醒、联网且 `npm start` 持续运行的 7 天 soak 中，来源计划检查成功率不低于 95%，无重复通知；进程重启后任务自动恢复。
8. **一条命令启动**：完成一次 `npm ci` 和本地配置后，用户只执行 `npm start` 即可启动全部运行组件，不安装或启动 Docker、PostgreSQL、Redis 和远程服务。
9. **隐私合格**：生产 SQLite、日志、备份抽样和通知内容中不存在医院会话凭据或敏感身份信息，运行时无项目遥测或云同步。
10. **开源可复现**：未参与开发的用户从 GitHub `easy-hospital` 稳定标签克隆代码，按公开文档在受支持系统完成安装、启动、测试通知和备份恢复。

产品文案只能承诺“应用运行且本机联网期间监测公开信息并提醒”，不能使用“秒抢”“必中”“实时保证”“自动挂号”“关机也能监测”等表述。

这里的“上线”指在 GitHub `easy-hospital` 发布首个稳定版本。以下门槛全部满足才可创建稳定标签；任一项失败均为 No-Go：

| 门槛 | 放行条件 | 证据 |
|---|---|---|
| G-01 决策冻结 | 第 12.1 节已决策项落实；PD-01～PD-05 均有明确选择；若选择 B 级 P0，US-P1-01 已迁入并通过 P0 | 决策记录与冻结版 PRD |
| G-02 P0 完整 | US-P0-01～US-P0-13 的每条验收标准通过 | 验收清单、自动化报告、人工验收记录 |

| G-04 无 Docker | 运行代码、发布物和安装文档均不包含 Docker/Compose 方案，也不依赖 PostgreSQL、Redis 或远程项目服务 | 依赖清单、仓库扫描、出站网络抓包 |
| G-05 稳定开源 | GitHub `easy-hospital` 公开可读；许可证、README、贡献指南、安全渠道、变更记录、锁文件和语义化发布说明完整；所有受支持平台必需 CI 通过 | 仓库设置、CI、发布候选标签 |
| G-06 目标与内容 | 两个首批目标规则均在 30 天内由官方来源核验，URL 可访问 | 规则页面截图、来源 URL、核验日期 |
| G-07 真实来源 | 至少一个状态来源完成本机 7 天 soak；计划检查成功率 ≥95%，随机 10 次人工比对 100% 一致 | 健康导出、比对记录 |
| G-08 通知闭环 | 真实设备 2 分钟内收到测试通知；放号提醒误差 ≤±30 秒；事件通知 P95 ≤60 秒 | 渠道回执与时间戳 |
| G-09 故障恢复 | 来源失败、SQLite 写入失败、Job Runner 中断、主进程退出和本机休眠恢复场景通过；无已提交事件丢失或重复通知，空窗不被误报 | 故障演练记录 |
| G-10 安全隐私 | 敏感字段和 Git 历史扫描为 0；密钥仅由本地环境注入；无遥测、云同步、登录录入和自动预约能力 | 扫描报告、抓包、配置审查 |
| G-11 访问克制 | 请求频率、串行限制、退避和官方限制均符合第 4.5 节；无代理与风控绕过 | 7 天请求日志抽样 |
| G-12 可接管 | 未参与开发的验收者按公开文档完成安装、单命令启动、健康查看、测试通知、备份恢复、升级与卸载 | 操作记录 |
| G-13 文案合规 | 所有页面和通知均有来源、检测时间、仅运行期间监测、官方为准和非自动挂号声明 | 产品文案检查表 |

P1 不阻塞上线，唯一例外是 PD-02 把 B 级来源提升为 P0。

## 11. 风险与依赖

### 11.1 风险

| 风险 | 概率/影响 | 缓解措施 | 触发的 No-Go 条件 |
|---|---|---|---|
| 官方页面改版导致解析失效 | 高/高 | SourceAdapter 隔离、内容哈希、固定夹具、失败转 `unknown`、健康告警 | 7 天成功率低于 95% 或存在把异常判为无号 |
| 首批目标无可用 A 级状态来源 | 高/高 | A 级先行探测；C 级诚实降级；由 PD-02 决定是否引入 B 级 | 仍宣传状态/退号监控但没有通过门槛的 A/B 来源 |
| 访问触发限流或违反来源规则 | 中/高 | 5 分钟最短周期、同源复用、单并发、指数退避、遵守官方更低频限制 | 需要代理、账号轮换、验证码绕过才能工作 |
| 状态语义映射错误造成误报 | 中/高 | 三态模型、未知不当无号、夹具回放、真实人工抽查 | 随机比对存在任何状态不一致且未修复 |
| “退号”推断误导用户 | 中/中 | 30 分钟窗口、仅明确状态转换、统一称“疑似退号回流” | 文案声称确定退号或保证可挂 |
| 规则过期导致错误定时提醒 | 中/中 | 30 天复核标记、90 天降可信度、通知携带核验日期 | 首批规则超过 30 天仍无警示 |
| 通知渠道延迟或不可达 | 中/高 | 真实设备验收、有限重试、失败可见；P1 支持备渠道 | 测试通知无法在 2 分钟内送达 |
| 本机休眠、关机、断网或终端被关闭 | 高/高 | 首页常驻显示运行状态与空窗；恢复先建基线；文档要求 soak 时禁用休眠 | 应用声称离线期间持续监测，或恢复后推断空窗事件 |
| 单进程崩溃造成监测中断 | 中/中 | SQLite 持久任务/发件箱、优雅退出、启动恢复、进程锁 | 已提交事件丢失、重复通知或两个实例并发查询 |
| SQLite 文件损坏或升级不兼容 | 低/高 | WAL、启动前完整性检查、升级前备份、向前迁移和失败回滚 | 备份无法恢复或升级破坏现有任务 |
| 开源发布泄露密钥或本地数据 | 低/高 | `.gitignore`、字段白名单、全历史扫描、发布清单 | 仓库历史发现真实密钥、会话、日志或 SQLite 文件 |
| 依赖供应链或跨平台行为漂移 | 中/高 | 锁文件、最小依赖、受支持平台 CI、Dependabot/安全公告评估 | 任一高危未处置漏洞或受支持平台无法启动 |
| 深链变化或需要额外 App | 中/中 | 保存官方落地页而非脆弱私有协议，定期人工点击核验 | 首批官方入口不可达 |
| Playwright 下载体积或资源占用过高 | 中/中 | A 级接口优先；浏览器按需启动、限制并发、文档披露磁盘需求 | 受支持本机无法稳定通过 7 天 soak |

## 13. 发布与回滚原则

- 首次“上线”是在公开 GitHub `easy-hospital` 创建稳定版本；应用仍只在每个用户本机运行，不提供注册网址或项目后端。
- 适配器或规则更新必须可单独停用；某来源异常时停用该来源不会影响规则页、其他来源和已有历史记录。
- 发布前停止应用并备份 SQLite 数据文件和本地配置；备份不得提交 Git。
- 若新版本事件判定异常，停止本地进程，恢复上一稳定 GitHub 标签对应版本与升级前 SQLite 备份，暂停状态通知，避免批量误报。
- 数据迁移必须先复制备份、在事务中执行并记录 schema 版本；迁移失败时启动中止，不得在半迁移数据库上继续监测。
- 回滚后不补发停机期间无法确定的状态变化；恢复时先建立基线，并在界面记录监测空窗。
- 一旦发现敏感凭据落库、出现项目遥测、绕过风控或重复通知风暴，立即停止本地主进程，保留脱敏故障证据，完成清理和验证后再恢复。
